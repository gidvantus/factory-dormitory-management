# Персонал

Рабочий раздел: `/cabinet/personnel`. Демонстрационный макет `/preview/personnel` остаётся отдельным и не меняет рабочие данные.

## Карточки и таблицы

`employees.id` — постоянный UUID человека. Строки «Проживающих», «Притока», «Оттока», архива и пользовательских таблиц хранят `employee_id`. ФИО, табельный номер и телефон остаются в исходных строках: сведения из разных общежитий могут отличаться.

Создание записи из интерфейса сначала вызывает `/api/personnel/check`. Если пользователь выбирает совпадение, используется существующая карточка; без выбора создаётся новый сотрудник со статусом `confirmed`. Отдельные переключатели «Новый человек» и «Пока не могу определить» убраны из общей формы. Выбор можно снять. Перед записью сервер повторяет проверку под общим транзакционным замком PostgreSQL. Изменившийся результат требует повторной проверки. Совпадение фамилии или табельного номера не объединяет людей автоматически; отсутствие общих данных не позволяет гарантированно найти дубль. Старые временные карточки со статусом `pending` сохраняются.

Старые маршруты добавления пустой строки сохранены для совместимости. При первом заполнении такой строки создаётся временная карточка. В «Проживающих», «Притоке», «Оттоке», архиве и пользовательских таблицах нажатие на ФИО открывает карточку поверх текущей таблицы, карандаш включает редактирование имени. В архиве и пользовательских таблицах используется сопоставленный столбец ФИО; если он скрыт или не настроен, карточка доступна через «Действия» → «Открыть сотрудника». Привязку строки можно исправить через «Изменить связь» внутри карточки: проверка предложит существующих людей по известным данным.

Для пользовательских таблиц и архива поля сопоставляются с ID столбцов через «Связь с персоналом». Переименование столбца сохраняет связь. Сопоставление не объединяет людей автоматически.

При действии «Отток» в «Проживающих» указываются причина и дата выезда. Если в «Оттоке» есть действующий выпадающий столбец «Причина» / «Причины», используются его варианты. Для текстового столбца доступны ранее сохранённые причины и ввод новой; новые причины сохраняются для этого общежития и столбца даже после удаления записи оттока. Дата по умолчанию — текущий день (либо скопированная дата выезда), её можно изменить. Если соответствующий столбец скрыт или отсутствует, поле не отображается, а форма объясняет, что добавить или восстановить. В «Общем отчёте» можно выбрать причину из того же списка и распределять количество записей по дате выезда. При пользовательских столбцах значения записываются в их ячейки, а стандартные поля причины и даты сохраняют сведения для истории сотрудника. Миграция `0035_outflow_reasons` добавляет только справочник текстовых причин.

## История и объединение

В «Притоке» действия «Заселить» и «В отток» создают новую строку в «Проживающих» или «Оттоке» с тем же `employee_id`. Исходная строка сохраняется и получает `processed_as`, `processed_row_id` и `processed_at`: это исторический результат, который остаётся даже после удаления строки назначения. Повторная обработка любой из двух команд запрещена. При заселении также проверяется, что сотрудник ещё не числится проживающим, включая другие общежития и ранее объединённые карточки.

Переносятся только активные столбцы с однозначным совпадением названия и типа (регистр и лишние пробелы не учитываются). Выпадающие значения сопоставляются по названию варианта и записываются с ID варианта назначения. Несовпадающие, скрытые и несовместимые поля остаются только в исходной строке. Окно подтверждения показывает имя сотрудника и действие без списков переносимых и пропущенных столбцов. «Дата заселения» не подменяет автоматически «Начало вахты». Для «В отток» используется та же форма причины и даты, что для проживающих, включая справочник причин, подсказки отсутствующих столбцов и связь с общим отчётом. Снимок столбцов и исходных данных защищает от переноса устаревших значений. Новые строки притока, проживающих и оттока отображаются первыми.

Маршруты `/api/dormitories/{id}/inflow/{row_id}/{settle|outflow}/preview` готовят перенос, маршруты без `/preview` подтверждают его. Миграция `0036_inflow_actions` добавляет только nullable-поля результата обработки, существующие строки остаются необработанными. Новые служебные действия добавляются в старую структуру таблицы при её чтении; явно скрытые действия не восстанавливаются автоматически.

События `employee_events` сохраняют снимки исходных данных, общежитие, дату и автора. Обновление строки, перевод, отток и удаление записываются в той же транзакции, что и исходная операция. Перевод и оформление оттока сохраняют ID человека. История удалённой строки остаётся доступной; сведения, удалённые до внедрения раздела, восстановить нельзя.

Вкладка «Совпадения», экран сравнения двух карточек, общий расчёт пар в сводке и команды `/api/personnel/merge` / `/api/personnel/separate` удалены. Проверка при добавлении и привязке записи продолжает работать через `/api/personnel/check`, `/records` и `/link`. Выбор существующего сотрудника создаёт новую связанную строку, а не новую карточку человека.

Ранее выполненные объединения через `merged_into_id` сохраняются: сводка и карточка собирают исходные строки, события, заметки и планы всей группы. В истории остаются сведения об этих объединениях и возможность отменить старое объединение. При отмене исходные данные снова разделяются; добавленные после объединения записи остаются у выбранной основной карточки. Сохранённые решения прежнего экрана «разные сотрудники» остаются в базе, но новые не создаются и общий поиск пар их больше не использует. Миграция данных для удаления вкладки не требуется.

Сводка считает карточки, а не строки. Пока остаются временные карточки или несколько записей текущего проживания у одного человека, интерфейс сообщает о необходимости проверки.

## Работа

Продление меняет `Resident.shift_end`. Согласованный выезд не завершает проживание; фактический отток оформляется из исходной таблицы.

«План заездов» — таблица действующих общежитий по датам. Одна запись на общежитие и день хранит вручную указанное количество (1–10000) и необязательные ФИО, каждое с новой строки. ФИО можно указать частично; их число не должно превышать количество приезжающих. Запись можно изменить или удалить. Ревизия защищает от перезаписи изменений из другого окна.

План не создаёт карточки сотрудников, не меняет проживание и не закрывается автоматически при заселении. Для строки «Общего отчёта» внутри общежития выберите «Связь с таблицей» → «План заездов». За каждую дату подставляется введённое количество, при отсутствии записи — 0. Количество ФИО не участвует в расчёте. Данные доступны для формул и экспорта отчёта; изменение или удаление плана меняет связанные значения. Архивирование общежития скрывает его из планирования, сохраняя данные в отчёте. Шаблоны отчёта переносят только связь, без значений плана.

Маршруты `/api/personnel/arrivals`: POST — создание; PUT `/{id}` — исправление с ревизией; DELETE `/{id}?revision=N` — удаление. Старые индивидуальные планы сохранены для совместимости и истории, но новая вкладка их не использует. Форма «Следующая вахта» и фильтр сотрудников по индивидуальным заездам убраны из рабочего интерфейса.

В конструкторах блоков дашборда и статистики доступен отдельный источник «План заездов» (`arrival_plan`). Он читает те же записи напрямую, без промежуточной строки общего отчёта. Можно показать общую сумму, список по общежитиям или график по дням; статистика также поддерживает таблицы и свои виды диаграмм. Для дней без плана берётся 0. Будущие даты учитываются на всём выбранном периоде только для этого источника; остальные источники сохраняют ограничение текущей датой. Для числа и списка на дашборде по умолчанию выбирается сумма за период; вариант «На последнюю дату периода» берёт только этот день. При выборе всех общежитий новые добавляются в расчёт автоматически, исключения сохраняются. Архивные общежития доступны для исторических расчётов. Исправление и удаление записей отражаются при следующем обновлении данных блока. Дополнительная миграция для источника не требуется.

В разделе персонала остались три вкладки: «Рабочая поверхность», «Сотрудники» и «План заездов». Кнопка «Добавить блок» доступна только на рабочей поверхности. Во вкладке «Сотрудники» доступны только «Все сотрудники», «Проживают» и «Заканчивается вахта». Удалены остальные фильтры, избранное «Мои сотрудники», блоки «Неполные данные» и «История оттока», их счётчики и переходы. История, вахты и заметки в карточке человека и проверка совпадений при вводе продолжают работать независимо от фильтров списка.

Заметки и планы общие для пользователей с действующим доступом к проекту, как и существующие таблицы общежитий. Блоки и сохранённые списки сохраняются отдельно для пользователя. Ревизия настроек защищает от перезаписи изменениями из другого окна.

## Миграция и проверки

`0023_personnel` создаёт таблицы раздела и ссылки из исходных таблиц. Каждая непустая существующая стандартная строка получает отдельную карточку со статусом `pending` и начальное событие. Автоматического объединения нет. Перед применением нужна резервная копия базы. Откат миграции удаляет данные нового раздела, поэтому после начала работы для восстановления нужна резервная копия.

`0031_remove_personnel_tasks` удаляет таблицу задач, события задач и соответствующие блоки из пользовательских настроек. Остальные блоки, списки, избранное, заметки и планы сохраняются. Откат возвращает пустую таблицу задач; удалённые данные восстанавливаются из резервной копии.

`0032_arrival_plans` создаёт `arrival_plans` и копирует прежние индивидуальные заезды, группируя по общежитию и дате. Исходные данные сохраняются. Стандартные названия блоков обновляются; старый фильтр `arrivals` в сохранённых списках заменяется на `all`. Откат удаляет новую таблицу вместе с её данными; для восстановления нужна резервная копия.

Проверки: `tests/test_personnel.py`, общие тесты переводов и оттока, `src/workspace/personnel/personnel.test.tsx` и тесты добавления строк трёх стандартных таблиц.

`0034_simplify_personnel_filters` удаляет из пользовательских настроек избранное, списки с удалёнными фильтрами, блоки «Неполные данные» / «История оттока» и блоки, ссылающиеся на удалённые списки. Ревизия увеличивается только у изменённых настроек. Остальные списки и блоки, исходные таблицы, карточки, история, заметки и планы сохраняются. Перед применением нужна резервная копия; откат возвращает пустое избранное для совместимости, а удалённые настройки восстанавливаются из копии.

# Письма: шаблоны в `mail_templates`

Письма не лежат в коде: тема, plain-текст и вёрстанная HTML-часть живут строками
таблицы `mail_templates`, поэтому формулировку можно поправить в базе без
релиза. Отправляет письма единственное место — `app/backend/app/mail.py`.

## Коды шаблонов

| `code` | Когда уходит | HTML-часть |
|---|---|---|
| `activation` | после самостоятельной регистрации | вёрстанная, ревизия `0059_mail_html_bodies` |
| `invitation` | администратор пригласил сотрудника в организацию | вёрстанная, ревизия `0059_mail_html_bodies` |
| `password_recovery` | запрос на смену забытого пароля | нет (`NULL`), прежняя обёртка |

Других кодов нет, и добавлять их «на будущее» не нужно: отсутствие шаблона — это
`MailTemplateNotFound`, письмо в этом случае не уходит (приглашение и регистрация
при этом не падают, а пишут ошибку в лог).

## Две части одного письма

Письмо уходит как `multipart/alternative`, то есть у него два представления:

* **`body`** — plain-текст. Это то, что видит клиент без HTML и что попадает в
  превью. Строки переносятся `\n`, разметки здесь нет и быть не должно.
* **`body_html`** — вёрстанная HTML-часть: письмо целиком, от `<html lang="ru">`
  до `</html>`, с инлайновыми стилями (разметка — по макету `mockups/154` из
  issue #154).

`body_html` nullable. Если колонка пуста или `NULL`, HTML-часть собирается из
plain-текста прежней обёрткой (`Arial 15px #27313D` с `<br>`) — так уходит
`password_recovery` и любой шаблон, которому разметку ещё не завели.

**Правка одной части не меняет другую.** Меняете текст письма — правьте обе
колонки: иначе получатель в HTML-клиенте увидит старое, а в plain-клиенте новое.

## Плейсхолдеры

Подстановка одна для темы, plain-текста и HTML:

| Плейсхолдер | Что подставляется |
|---|---|
| `{full_name}` | имя получателя (`users.full_name`) |
| `{activation_url}` | абсолютная ссылка вида `<frontend_base_url>/activate/<token>` |
| `{expires_hours}` | срок жизни ссылки в часах (`ACTIVATION_TOKEN_TTL_HOURS`, по умолчанию 24) |
| `{organization_phrase}` | ` организации «Ромашка»` для приглашения; пустая строка, если у организации нет названия |
| `{site_url}` | `frontend_base_url` без хвостового `/` — для ссылок подвала |
| `{subject}` | тема письма; нужен только в `<title>` HTML-части |

Правила подстановки:

* в **HTML** значения экранируются (`html.escape(value, quote=True)`) до вставки
  в разметку, поэтому имя `Иванов <Иван> & Ко` придёт текстом, а не тегом. Сама
  разметка шаблона не экранируется;
* в **plain-тексте** экранирования нет: там `&` и `<` — обычные символы;
* незнакомый плейсхолдер даёт пустую строку (а не `KeyError`): шаблон правят в
  базе, и опечатка не должна оставлять пользователя без письма;
* незакрытая скобка в шаблоне логируется, письмо уходит с сырым текстом;
* после подстановки в HTML не должно остаться ни одной `{` — это проверяют тесты
  `app/backend/tests/test_mail.py` и `test_mail_html_migration.py`.

## Чего в письмах нет намеренно

Картинок, `<img>`, спрайтов, SVG, внешних CSS и шрифтов по ссылке в письмах нет:
логотип-домик нарисован типографикой и CSS (треугольник и рамка), поэтому хостинг
ассетов и пересборка образа `web` для писем не нужны. `<style>`-блоков и
`flex`/`grid`/`position:absolute` тоже нет — только инлайновые стили и табличная
раскладка `role="presentation"`, иначе Gmail и Outlook вырежут половину вёрстки.

Токен активации живёт только в ссылке письма: ни в логах, ни в тексте ошибок его
нет.

## Миграции

HTML-части двух писем заводит ревизия `0059_mail_html_bodies` (аддитивная:
добавляет колонку и заполняет две существующие строки). `downgrade` снимает
только колонку; plain-тексты писем остаются на месте. Схема и миграция едут в
одном PR.

# Деплой на боевой сервер

Ручной деплой: GitHub Actions → «Деплой на боевой сервер» → «Run workflow».
Один workflow — `.github/workflows/deploy.yml`, один сервер, один каталог
`/srv/crm-dormitory`. Образец — `.github/workflows/deploy.yml` проекта Vahta,
переписанный под этот стек: `db + api + web + bot` (+ `caddy` по профилю `tls`).

## Что делает workflow и почему только он

Деплой идёт **только** через Actions, руками на сервере ничего не выкатывается:

- код на сервер приезжает архивом из ветки `develop-m`
  (`git archive HEAD`), а не `git pull` — на сервере нет рабочей копии
  с правами на репозиторий, и подтягивать чужие коммиты оттуда нечем;
- `.env` сервера исключён из распаковки: настройки боевой базы и TLS деплой
  не перезаписывает;
- перед обновлением снимается дамп БД — единственная страховка от неудачной
  миграции (см. «Необратимое»);
- каждый шаг назван по стадии работы, поэтому по подсвеченному красным шагу
  видно, где встал деплой, без чтения всего лога.

`concurrency: group: crm-deploy, cancel-in-progress: false` — два деплоя не идут
параллельно: второй дожидается первого. Иначе две сборки и две миграции шли бы
по одной боевой базе одновременно.

## Необратимое

**Каждый деплой применяет `alembic upgrade head` к боевой базе.** Миграции
запускает сам контейнер `api` при старте (`app/backend/entrypoint.sh`), отдельного
шага миграций нет. Отката миграций не существует ни в коде, ни в workflow:
`alembic downgrade` в деплое не вызывается.

Страховка одна — шаг «Сервер: бэкап БД перед обновлением» (`pg_dump -Fc` в
`/srv/crm-dormitory/backups/`). Она спасает только на существующей базе и только
если дамп снялся успешно: на первом деплое (пустая база) бэкап пропускается с
предупреждением, откатывать там нечего.

Первое «да» на запуск даёт человек: пока доступов к серверу нет, workflow
падает на шаге «Проверка: секреты деплоя заданы» и до SSH не доходит.

## Секреты репозитория

Задаются в `Settings → Secrets and variables → Actions → New repository secret`.

| Секрет | Что это | Откуда брать |
|---|---|---|
| `CRM_SSH_KEY` | приватный ключ SSH (весь файл, включая `-----BEGIN`/`-----END`) | тот ключ, чья публичная часть лежит в `~/.ssh/authorized_keys` пользователя деплоя на сервере |
| `CRM_SSH_HOST` | адрес сервера (IP или DNS-имя) | у человека, который завёл сервер; в репозитории его нет и быть не должно |
| `CRM_SSH_USER` | пользователь деплоя (не `root`, если можно иначе) | создаётся на сервере, состоит в группе `docker` |
| `CRM_SSH_PORT` | SSH-порт | по умолчанию `22`; задавать, только если порт менялся |

Ключ копируется целиком и **без CRLF**: приватный ключ, перенесённый с
Windows-машины, приходит с `\r`, ssh такой файл не читает. Workflow чистит `\r`
(`tr -d '\r'`), но и его проверка на этом шаге упасть может — тогда ключ надо
пересохранить в unix-переводах строк.

Домена и адреса сервера в репозитории нет ни в одном файле: хост приходит из
секрета, домен — из `SITE_DOMAIN` в `.env` сервера.

## Подготовка сервера (один раз)

1. Docker Engine и плагин `docker compose` (`docker compose version`).
2. Каталог проекта: `/srv/crm-dormitory` (`REMOTE_DIR` в workflow), владелец —
   пользователь деплоя. Распаковка делает `rsync -a --delete`, поэтому каталог
   должен принадлежать этому пользователю.
3. `.env` в `/srv/crm-dormitory`, собранный по чек-листу `docs/ssl.md`:
   `SITE_DOMAIN`, `ACME_EMAIL`, `CADDY_ACME_CA`, `FRONTEND_PORT=127.0.0.1:8081`,
   `API_PORT=127.0.0.1:8001`, `FRONTEND_BASE_URL=https://<домен>`,
   `SESSION_COOKIE_SECURE=true`, плюс секреты базы из `.env.example` и токены
   бота `TELEGRAM_BOT_TOKEN`, `TELEGRAM_SERVICE_TOKEN`.
   Токены бота нужны не «когда-нибудь потом»: без них `app/bot/__init__.py`
   пишет в лог `Бот не запущен: не заданы …` и выходит, контейнер `bot` уходит
   в рестарт по кругу (`restart: unless-stopped`), и шаг запуска стека падает на
   `--wait`. Поэтому они проверяются до запуска, вместе с остальными.
   Шаг «Сервер: проверка .env по чек-листу TLS» падает, если чего-то нет, если
   `FRONTEND_PORT`/`API_PORT` не начинаются с `127.0.0.1` или если
   `SESSION_COOKIE_SECURE` не `true`.
4. `COMPOSE_PROJECT_NAME=crm-dormitory-prod` в том же `.env`: имя проекта
   фиксируется, иначе оно зависело бы от имени каталога. Из `.env` же его берёт
   `docker compose`, поэтому в workflow флаг `-p` не передаётся.
5. Одна A-запись домена на адрес сервера (и `www`), без AAAA и без прокси/CDN —
   ACME должен получить прямой ответ на портах 80 и 443 (`docs/ssl.md`).
6. Порты 80/443 на машине должны быть свободны: стенд Vahta занимает их на
   своём сервере, CRMDormitory нужен отдельный сервер или своя цепочка прокси.

## Диагностика: шаг → что делает → типичная ошибка

Шагов в workflow ровно семнадцать, таблица повторяет их порядок и имена.

| № | Шаг | Что делает | Типичная ошибка |
|---|---|---|---|
| 1 | `Checkout` | клонирует ветку в раннер | закончились минуты Actions или упала сеть GitHub |
| 2 | `Проверка: деплой только из ветки develop-m` | пускает запуск только из `refs/heads/develop-m` | нажали «Run workflow», выбрав `main` или ветку задачи: шаг красный, деплой не начался — это защита от выкатки устаревшего `main` |
| 3 | `Проверка: секреты деплоя заданы` | перечисляет отсутствующие `CRM_SSH_KEY`/`CRM_SSH_HOST`/`CRM_SSH_USER` и падает | секреты не заведены или заведены в Environment вместо Repository: пока их нет, падение обязано быть здесь, до SSH |
| 4 | `Ревизия: какой коммит поедет на сервер` | печатает ветку, `github.sha`, `git log -1` | ошибки нет; шаг нужен, чтобы в логе деплоя остался точный коммит |
| 5 | `SSH: настроить ключ доступа` | пишет ключ в `~/.ssh/id_ed25519`, чистит CRLF, проверяет читаемость `ssh-keygen -y` и заводит псевдоним `crm-deploy` в `~/.ssh/config` (ключ, порт, `BatchMode`, `ConnectTimeout`) — дальше все шаги обращаются к серверу только по нему | ключ скопирован с CRLF или обрезан (нет `-----END`): `ssh-keygen` не читает файл |
| 6 | `SSH: проверка подключения` | `ssh` с `BatchMode=yes`, печатает `===SSH-OK===`, `hostname`, `whoami` | публичная часть ключа не в `authorized_keys`, не тот пользователь, закрыт порт, `CRM_SSH_HOST` указывает не туда — `Permission denied (publickey)` или таймаут |
| 7 | `Сервер: проверка .env по чек-листу TLS` | читает `.env` сервера и требует непустые `SITE_DOMAIN`, `ACME_EMAIL`, `CADDY_ACME_CA`, `FRONTEND_PORT`, `API_PORT`, `FRONTEND_BASE_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_SERVICE_TOKEN`, `SESSION_COOKIE_SECURE=true`; порты обязаны начинаться с `127.0.0.1` | файла нет, ключ пуст, `FRONTEND_PORT=8080` без `127.0.0.1` (тогда caddy не получит порт 80), `SESSION_COOKIE_SECURE` не `true`, не заданы токены бота (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_SERVICE_TOKEN`) — сообщение называет отсутствующий ключ и отправляет в `docs/ssl.md` |
| 8 | `Сервер: бэкап БД перед обновлением` | ищет контейнер через `docker compose ps -aq db` (ошибка «нет compose-файла» на первом деплое глушится), снимает `pg_dump -Fc` в `backups/crm_<TS>.dump`; контейнера нет — `::warning::` и дальше, контейнер есть но остановлен — ошибка и стоп | нет места на диске, `POSTGRES_USER`/`POSTGRES_DB` пусты в окружении контейнера — `pg_dump` возвращает ошибку и шаг красный; «БД существует, но не запущена» значит, что база остановлена, а деплой пошёл бы с миграциями без страховки — поднять `docker compose --profile tls up -d db` и повторить |
| 9 | `Архив: упаковать и передать на сервер` | `git archive` в `/tmp/deploy.tar` и `scp` на сервер | архив не собрался из-за автоконвертации строк (`core.autocrlf` уже отключён) или `scp` упёрся в квоту и место в `/tmp` сервера |
| 10 | `Сервер: распаковка в $REMOTE_DIR` | `tar -xf` в `/tmp/crm-deploy-stage` и `rsync -a --delete` с исключениями `.env` и `backups/` | нет прав на `/srv/crm-dormitory` (каталог принадлежит другому пользователю); исключения сломаны — тогда уехали бы `.env` и дампы, поэтому их ровно два и `.env*` исключать нельзя (`.env.example` обязателен compose) |
| 11 | `Сервер: сборка образов` | `docker compose --profile tls build` в `/srv/crm-dormitory` | кончилось место под образы, долгая сборка фронта по памяти, ошибка в `Dockerfile` — старый контейнер при этом ещё работает, простой не начался |
| 12 | `Сервер: запуск стека (здесь же миграции)` | `docker compose --profile tls up -d --no-build --remove-orphans --wait --wait-timeout 180`; миграции применяет `api` при старте | упавшая миграция роняет `api` и этот шаг; пустые `TELEGRAM_BOT_TOKEN`/`TELEGRAM_SERVICE_TOKEN` в `.env` роняют `bot` в рестарт по кругу, и шаг тоже красный (но такие `.env` отсекает шаг 7 — если красный всё-таки здесь, смотрите `docker compose logs bot`); `--wait` проверяет только `db` и `caddy` — у `api`/`web`/`bot` healthcheck'ов нет, поэтому зелёный шаг ещё не значит «стек жив» |
| 13 | `Сервер: ANALYZE после миграций` | находит контейнер БД через `docker compose ps -q db` и выполняет `psql -c 'ANALYZE'` | контейнер БД не найден (стек не поднялся) или `psql` недоступен в образе БД — шаг красный, деплой остановлен |
| 14 | `Сервер: перечитать конфиг caddy` | `docker exec <id> caddy reload --config /etc/caddy/Caddyfile`, при ошибке — `up -d --force-recreate caddy` | `reload` падает на синтаксисе `Caddyfile`; тогда контейнер пересоздаётся, сертификаты переживают это в томе `caddy_data` — том не удалять |
| 15 | `Проверка: /healthz по HTTP на сервере` | `curl http://localhost/healthz`, требует 200 | caddy не поднялся или сломан блок `:80` в `caddy/Caddyfile` (он обязан отдавать 200 без редиректа) |
| 16 | `Проверка: /api/health по HTTPS` | читает `SITE_DOMAIN` из `.env` и делает `curl --resolve <домен>:443:127.0.0.1 https://<домен>/api/health`, требует 200 и `"status":"ok"` | нет A-записи или сертификат не выпущен (ошибка TLS), `api` упал после старта, nginx фронта не проксирует `/api/` — здесь единственная настоящая проверка работоспособности API |
| 17 | `Итог: деплой завершён` | печатает `github.sha`, домен и `docker compose ps` | ошибки нет; по `ps` видно, все ли контейнеры `running` |

## Первый деплой (чистый сервер)

1. Сервер подготовлен по разделу «Подготовка сервера», `.env` заполнен.
2. Actions → «Деплой на боевой сервер» → «Run workflow» → ветка `develop-m`.
3. Шаг бэкапа печатает `::warning::Контейнер БД не запущен — это первый деплой
   на чистом сервере` и пропускается: база создаётся этим же запуском, откатывать
   нечего.
4. Первый выпуск сертификата удобно делать на staging ACME
   (`CADDY_ACME_CA=https://acme-staging-v02.api.letsencrypt.org/directory`), затем
   вернуть боевую директорию — порядок в `docs/ssl.md`. **Пока стоит staging,
   шаг 16 ожидаемо красный**: staging-сертификат не в доверенных, `curl` без `-k`
   получает код 60 и пустое тело. Это не сбой стека и не повод искать A-запись:
   верните в `.env` боевую `CADDY_ACME_CA`, перезапустите caddy (шаг 14 сделает
   это сам) и запустите деплой ещё раз.
5. Итог: шаг 15 и шаг 16 зелёные, `docker compose ps` показывает `db`, `api`,
   `web`, `bot`, `caddy`.

## Откат

Автоматического отката нет: workflow не возвращает ни образы, ни схему.

**Данные.** Сначала останавливаем писателей, потом восстанавливаем дамп:

```bash
# на сервере, в /srv/crm-dormitory
docker compose --profile tls stop api bot
DB="$(docker compose ps -q db)"
DB_USER="$(docker exec "$DB" printenv POSTGRES_USER)"
DB_NAME="$(docker exec "$DB" printenv POSTGRES_DB)"
docker cp /srv/crm-dormitory/backups/crm_<TS>.dump "$DB":/tmp/restore.dump
docker exec "$DB" pg_restore -U "$DB_USER" -d "$DB_NAME" --clean --if-exists /tmp/restore.dump
docker exec "$DB" rm -f /tmp/restore.dump
```

**Схема.** Дамп несёт и схему, поэтому восстановление возвращает базу к тому
состоянию, в котором её снял шаг 8. Отдельного `alembic downgrade` в откате нет.

**После восстановления `api` и `bot` остаются остановленными** — сайт отдаёт 502
до тех пор, пока их не поднимут. Поднимает их только повторный деплой после
`revert`: обычный `docker compose --profile tls up -d api bot` снова накатит
`alembic upgrade head` и вернёт ту схему, от которой вы только что откатились
(а `bot` без живого `api` всё равно не работает). Поэтому порядок такой:
восстановили дамп → сделали `revert`-коммит в `develop-m` → запустили деплой,
и он поднимает стек уже на старых миграциях. Если откатывать код не нужно
(revert не требуется), запускать деплой всё равно придётся: без него `api` и
`bot` останутся лежать.

**Код.** Гвард пускает деплой только из `develop-m`, поэтому откат кода — это
`revert`-коммит в `develop-m` через pull request и повторный запуск workflow.
Запускать деплой из другой ветки или из `main` нельзя: шаг 2 его не пропустит,
и это намеренно.

## Что не автоматизировано

- **Автоотката нет.** Плохой деплой откатывается руками по разделу «Откат».
- **Healthcheck'ов у `api`, `web` и `bot` нет.** `docker compose up --wait`
  проверяет только `db` и `caddy`, поэтому единственная настоящая проверка
  работоспособности — шаги 15 и 16. Healthcheck'и для этих сервисов — отдельная
  задача, эта их не добавляет.
- **Ротации бэкапов нет.** `backups/crm_<TS>.dump` копится, чистить его и
  выгружать в S3 нужно отдельной задачей (в Vahta это отдельный шаг workflow,
  здесь его нет).
- **CI и гейта тестов нет.** Деплой запускается вручную и не ждёт прогонов
  `pytest`/`vitest`: на момент этой задачи в репозитории нет ни `.github`, ни CI.
- **Мониторинга и ежедневного бэкапа по расписанию нет.**

## Кнопка «Run workflow» и ветка `main`

Файл workflow должен один раз попасть в `main` (ветка по умолчанию): GitHub
показывает `workflow_dispatch`-workflow в списке Actions только если он есть в
ветке по умолчанию. Пока файла в `main` нет, кнопки «Run workflow» не будет —
сам деплой при этом всё равно запускается только из `develop-m` (шаг 2).

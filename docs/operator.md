# Кабинет оператора

Отдельное приложение рядом с основным кабинетом: вход по логину и паролю из
конфига, список организаций платформы и карточка организации с правкой
реквизитов, реестр счетов, прайс платформы с правкой тарифов. Своей базы и своих
данных у кабинета нет: организации, счета и тарифы кабинет **не хранит** — читает
и правит он их в основном API по внутренней сети и сервисному токену
(`X-Operator-Token`), поэтому источник правды, правила и журнал остаются в
основном приложении.

Создания и удаления организаций в кабинете нет, миграций в задаче не было.
Завести тариф из кабинета тоже нельзя: прайс приходит из миграций базы, а
кабинет умеет только править строки и снимать их с продажи (см. «Тарифы»).

## Что где лежит

```
operator/
├── backend/            — FastAPI: вход, проверка сессии, выход, health
│   ├── app/            — config.py, security.py, schemas.py, main.py, api/
│   ├── tests/          — pytest
│   └── Dockerfile
└── frontend/           — React + TypeScript + vite: вход, список и карточка,
    │                     счета, тарифы, пользователи
    ├── src/            — api/, auth/, components/, lib/, pages/, test/
    ├── nginx.conf      — статика SPA и прокси /api/ в operator-api
    └── Dockerfile
```

Список, карточку и правку организаций, реестр счетов и прайс тарифов
кабинет-API не хранит: он проксирует их в основной API по внутренней сети с
сервисным токеном (`api/organizations.py`, `api/invoices.py`,
`api/tariffs.py`).

Оба сервиса объявлены в корневом `docker-compose.yml` — `operator-api` и
`operator-web`, без профиля: стенд поднимается одной командой, как раньше.

## Как поднять

```bash
docker compose up -d --build
```

Правка `.env` не нужна: умолчаний из `.env.example` достаточно, если порты
свободны.

Адреса по умолчанию:

- кабинет оператора — http://localhost:8081 (`operator-web`);
- API кабинета — http://localhost:8002 (`operator-api`);
- health обоих: `GET /healthz` у фронтенда и `GET /api/health` у API.

Если стендов на машине несколько, запускайте свой под отдельным именем
(`docker compose -p <имя> ...`): имя проекта и порты у каждого стенда свои.
Имя проекта Docker принимает только строчными буквами.

## Переменные `.env`

| Переменная | Значение по умолчанию | Что значит |
| --- | --- | --- |
| `OPERATOR_USERNAME` | `operator` | логин единственного оператора; не секрет |
| `OPERATOR_PASSWORD` | нет (в примере `change-me`) | пароль оператора; без него сервис не стартует |
| `OPERATOR_TOKEN_SECRET` | нет (в примере заглушка) | секрет подписи сессии кабинета, не короче 16 символов; **не** `JWT_SECRET` основного приложения |
| `OPERATOR_TOKEN_TTL_HOURS` | `12` | срок жизни сессии в часах; он же уходит в `Max-Age` cookie |
| `OPERATOR_SESSION_COOKIE_SECURE` | `false` | отдавать cookie только по https |
| `OPERATOR_API_PORT` | `8002` | порт API кабинета на хосте |
| `OPERATOR_FRONTEND_PORT` | `8081` | порт фронтенда кабинета на хосте |
| `OPERATOR_SERVICE_TOKEN` | нет (в примере заглушка) | сервисный токен контура «кабинет → основной API»; его читают **оба** сервиса (`api` и `operator-api`), потому что имя переменной у них одно. Пустое значение закрывает платформенные ручки основного API (`401`), а кабинет отвечает `503`. Это **не** `TELEGRAM_SERVICE_TOKEN` и не `OPERATOR_TOKEN_SECRET`: у каждого свои права |

Реальные значения `OPERATOR_PASSWORD`, `OPERATOR_TOKEN_SECRET` и
`OPERATOR_SERVICE_TOKEN` в репозитории не
хранятся: `.env.example` держит имена и заглушки, свои значения кладутся в `.env`.
На боевом стенде порты публикуются на `127.0.0.1` (см. `docs/ssl.md`).

## Контракт API

Всё под префиксом `/api` того же origin: nginx кабинета проксирует `/api/` в
`operator-api:8000`, поэтому cookie остаётся first-party. Схема — `/openapi.json`
и `/docs` на `operator-api`.

| Метод | Путь | Ответ |
| --- | --- | --- |
| `POST` | `/api/auth/login` | `200 {"username": "operator"}` и `Set-Cookie: operator_session=…; HttpOnly; SameSite=lax; Path=/; Max-Age=43200`; неверная пара — `401 {"detail": "Неверный логин или пароль"}` (один текст на неверный логин и неверный пароль) |
| `GET` | `/api/auth/me` | `200 {"username": "operator"}` или `401 {"detail": "Требуется авторизация"}` |
| `POST` | `/api/auth/logout` | `204` без тела, cookie гасится теми же атрибутами; без сессии — тоже `204` |
| `GET` | `/api/health` | `200 {"status": "ok"}` |
| `GET` | `/api/organizations?limit=50&offset=0` | `200 {"items": [{"id", "name", "inn", "created_at"}], "total": N}`, свежие сверху; `limit` 1..100, `offset` ≥ 0 |
| `GET` | `/api/organizations/{id}` | `200 {"id", "name", "inn", "kpp", "ogrn", "address", "created_at", "members_count", "dormitories_count"}`; архивные общежития в счётчике считаются, владелец в участниках тоже |
| `PATCH` | `/api/organizations/{id}` | `200` — тот же объект, что у карточки. Тело: `name`, `inn`, `kpp`, `ogrn`, `address`; кабинет-фронт отправляет все пять, `null` в реквизите очищает поле |
| `GET` | `/api/tariffs` | `200 [{"id", "name", "description", "amount", "currency", "period", "unit_label", "position", "is_visible", "max_members", "tooltip", "group_code", "price_label"}]` — **все** строки прайса, включая `is_visible = false`, порядок `position, id`; пагинации нет |
| `PATCH` | `/api/tariffs/{id}` | `200` — та же строка целиком, с пересчитанным `price_label`. Тело: только присланные поля из `name`, `description`, `amount` (строка `"4900.00"`), `period`, `max_members` (`null` — без ограничения), `is_visible` |
| `DELETE` | `/api/tariffs/{id}` | `204` без тела: `is_visible = false`, строка **не удаляется**; повторный вызов — тоже `204` |
| `GET` | `/api/solutions` | `200 [{"id", "code", "name", "description", "amount", "currency", "position", "is_visible", "price_label", "created_at", "updated_at"}]` — **все** строки каталога решений, включая `is_visible = false`, порядок `position, id`; пагинации нет. Периода оплаты в ответе нет: у решения нет своего срока, право действует по тарифу организации (#195), а `price_label` читается «500 ₽ разово» |
| `PATCH` | `/api/solutions/{id}` | `200` — та же строка целиком, с пересчитанным `price_label`. Тело: только присланные поля из `name`, `description` (`null` — описания нет), `amount` (строка `"500.00"`), `currency` (три заглавные латинские буквы), `position` (целое ≥ 0), `is_visible`. Поля `code` в теле нет, и `period` тоже нет: присланное отсекает `422` |
| `DELETE` | `/api/solutions/{id}` | `204` без тела: `is_visible = false`, строка **не удаляется** (на неё ссылаются `invoices.solution_id` и `organization_solutions`); повторный вызов — тоже `204` |

Сессия — httpOnly cookie `operator_session`, в JS токена нет.

Все ручки организаций — под сессией кабинета (без cookie `401 {"detail":
"Требуется авторизация"}`) и проксируют запрос в основной API
(`/api/platform/organizations`) с заголовком `X-Operator-Token`. Отказы данных
передаются **тем же кодом и тем же `detail`**, что и в основном API:

| Код | `detail` | Когда |
| --- | --- | --- |
| `404` | `Организация не найдена` | неизвестный `id` |
| `409` | `Организация с таким ИНН уже есть` | ИНН занят другой организацией |
| `422` | `Название не может быть пустым`, `ИНН должен состоять из 10 или 12 цифр` | правка с пустым названием или ИНН не по формату |
| `502` | `Основной API не принял сервисный токен` | основной API ответил `401` |
| `502` | `Основной API недоступен` | сеть, таймаут или `5xx` основного API |
| `503` | `Кабинет не настроен: не задан OPERATOR_SERVICE_TOKEN` | пустой секрет; в сеть запрос не уходит |

Ручки тарифов идут теми же путями через прокси (`operator/backend/app/api/tariffs.py`)
и отвечают теми же кодами и текстами, что основной API:

| Код | `detail` | Когда |
| --- | --- | --- |
| `404` | `Тариф не найден` | неизвестный `id` |
| `409` | `Тариф с таким названием уже есть` | название занято другой строкой, в том числе в другом регистре |
| `422` | `Название не может быть пустым`, `Название длиннее 120 символов`, `Цена не может быть отрицательной`, `Слишком большая цена`, `Цена должна быть числом`, `Неизвестный период оплаты`, `Количество пользователей не может быть отрицательным` | правка вне правил основного API; фронт снимает приставку `Value error, ` |
| `502` | `Основной API не принял сервисный токен` | основной API ответил `401` |
| `502` | `Основной API недоступен` | сеть, таймаут или `5xx` основного API |
| `503` | `Кабинет не настроен: не задан OPERATOR_SERVICE_TOKEN` | пустой секрет; в сеть запрос не уходит |

Текстом отказа владеет основной API: кабинет-API его не переписывает, а
фронтенд показывает дословно. `502` — не истёкшая сессия: кабинет при этом не
разлогинивает.

Ручки решений идут теми же путями через прокси
(`operator/backend/app/api/solutions.py`) и отвечают теми же кодами и текстами,
что основной API:

| Код | `detail` | Когда |
| --- | --- | --- |
| `404` | `Решение не найдено` | неизвестный `id` |
| `409` | `Решение с таким названием уже есть` | название занято другой строкой, в том числе в другом регистре |
| `422` | `Название не может быть пустым`, `Название длиннее 120 символов`, `Описание должно быть строкой`, `Цена не может быть отрицательной`, `Слишком большая цена`, `Цена должна быть числом`, `Валюта должна состоять из 3 заглавных латинских букв`, `Порядок должен быть целым числом`, `Порядок не может быть отрицательным`, `Слишком большой порядок`, `Состояние должно быть true или false` | правка вне правил основного API; фронт снимает приставку `Value error, ` |
| `422` | стандартный текст `pydantic` про лишнее поле | в теле `PATCH` пришёл `code` — он не правится — или `period`: периода оплаты у решения больше нет (#195) |
| `502` | `Основной API не принял сервисный токен` | основной API ответил `401` |
| `502` | `Основной API недоступен` | сеть, таймаут или `5xx` основного API |
| `503` | `Кабинет не настроен: не задан OPERATOR_SERVICE_TOKEN` | пустой секрет; в сеть запрос не уходит |

Публичный каталог магазина (`GET /api/solutions` основного API) этот раздел не
меняет: он по-прежнему отдаёт только `is_visible = true` и в том же порядке
`position, id`. Порядок витрины — **единственное**, что связывает две половины:
`position` из кабинета не пересчитывается на клиенте, а карточки магазина идут в
порядке ответа `GET /api/solutions`.

### Реквизиты поставщика (issue #179)

Это **единственное место**, где правятся реквизиты поставщика и строка про НДС.
Из них печатные формы счёта и акта (`app/backend/app/billing_forms.py`) собирают
блок «Исполнитель» в шапке, подпись исполнителя и «Банковские реквизиты» в
подвале, а строку про НДС печатают под итогом: пока не заполнено ни одного поля,
вместо блока реквизитов печатается заглушка «данные поставщика будут заполнены
позже», а пустая строка про НДС означает, что строки в документе нет вовсе (не
прочерк). Правка действует только на документы, собранные **после** неё: уже
выданный PDF лежит в хранилище и не перерисовывается
(`app/backend/app/invoice_files.py`), поэтому у старых счетов форма остаётся
прежней.

| Метод | Путь | Ответ |
| --- | --- | --- |
| `GET` | `/api/company-details` | `200 {"id": 1, "name", "inn", "kpp", "ogrn", "address", "bank_name", "bank_bic", "bank_account", "corr_account", "signatory", "vat_note", "updated_at"}` — все поля всегда присутствуют, пустые приходят как `null`; строки в базе нет — тоже `200` с пустыми значениями, а не `404` |
| `PATCH` | `/api/company-details` | `200` — та же строка целиком. Тело: **только присланные** поля из тех же одиннадцати; `null` и пустая строка после `strip()` очищают поле, отсутствующее поле не трогается |

Ручки открывает сессия кабинета и проксирует их в основной API
(`/api/platform/company-details`) с заголовком `X-Operator-Token`; создания
строки нет — её засеяла миграция `0067_company_details`. Отказы:

| Код | `detail` | Когда |
| --- | --- | --- |
| `422` | `ИНН должен состоять из 10 или 12 цифр`, `КПП должен состоять из 9 символов`, `ОГРН должен состоять из 13 или 15 цифр`, `БИК банка должен состоять из 9 цифр`, `Расчётный счёт должен состоять из 20 цифр`, `Корреспондентский счёт должен состоять из 20 цифр`, `Название длиннее 255 символов`, `Адрес длиннее 500 символов`, `Банк длиннее 255 символов`, `Подписант длиннее 300 символов`, `Строка про НДС длиннее 200 символов` | значение не по формату или длиннее колонки; фронт снимает приставку `Value error, ` |
| `404` | `Реквизиты поставщика не заведены` | строки нет в базе (не засеяна); кабинет её не создаёт |
| `502` | `Основной API не принял сервисный токен` / `Основной API недоступен` | как у остальных разделов |
| `503` | `Кабинет не настроен: не задан OPERATOR_SERVICE_TOKEN` | пустой секрет; в сеть запрос не уходит |

## Фронтенд

Маршруты:

- `/login` — форма входа: логин и пароль, ничего больше (восстановления пароля и
  регистрации у кабинета нет);
- `/` — список организаций под `RequireOperator`: при монтировании
  `GET /api/auth/me`, пока ждём — «Проверяем сессию…», `401` — редирект на
  `/login`. Шапка с логином и «Выйти» живёт на обоих экранах кабинета;
- `/organizations/:id` — карточка организации под той же проверкой сессии;
- `/tariffs` — прайс платформы: список, правка полей и снятие с продажи;
- `/solutions` — каталог решений магазина улучшений: список, правка полей,
  порядок витрины и снятие с продажи;
- `/company` — реквизиты поставщика и строка про НДС: форма из одиннадцати полей;
- остальные адреса редиректят на `/`.

Форма входа: пусто; отправка (кнопка неактивна, «Вход…»); клиентская проверка
пустых полей («Укажите логин», «Укажите пароль», запрос не уходит); отказ сервера —
текст `detail` дословно в `role="alert"`; сеть/`5xx` — «Не удалось войти.
Попробуйте ещё раз».

Список организаций:

- загрузка — «Загружаем организации…» в `role="status"`, счётчик не показывается;
- ошибка — текст `detail` дословно в `role="alert"` (в том числе «Основной API
  недоступен» и «Кабинет не настроен: не задан OPERATOR_SERVICE_TOKEN»);
- пусто — «Организаций пока нет»;
- заполненный реестр: `№`, «Название», «ИНН», «Создана», «Открыть»; счётчик в
  заголовке равен `total`; название `null` показывается как «Без названия»;
- «Показать ещё» догружает следующую страницу (`limit`/`offset`) и исчезает,
  когда показано столько же, сколько `total`.

Карточка организации: просмотр (реквизиты и счётчики участников и общежитий),
правка на месте (все пять полей), «Сохранить» отправляет все пять полей,
«Отмена» возвращает значения последнего ответа сервера. `404` — «Организация не
найдена» и ссылка «К списку». Отказ сохранения (`409`, `422`) показывается
дословно, введённые значения не сбрасываются, фокус возвращается в форму. На
отправке «Сохранить» неактивна и говорит «Сохраняем…».

Поиска и фильтров по списку нет: только постраничная выдача. Создания и удаления
организаций нет.

Прайс тарифов (`/tariffs`, макет `mockups/178/`):

- загрузка — «Загружаем тарифы…» в `role="status"`, счётчик не показывается;
- ошибка — текст `detail` дословно в `role="alert"` (в том числе «Основной API
  недоступен» и «Кабинет не настроен: не задан OPERATOR_SERVICE_TOKEN»);
- пусто — «Тарифов пока нет»: строки прайса приходят из миграций базы, завести
  тариф из кабинета нельзя;
- список: «Название», «Описание», «Цена», «Период», «Пользователей»,
  «Состояние», действия. Цену печатает готовый `price_label` ответа — формулу
  цены экран не повторяет и `period` в цену не подставляет. Состояние — слово
  «В прайсе» либо «Не в прайсе» с контурной точкой; `max_members = null` —
  «без ограничения». Счётчик в заголовке: «15 тарифов · 12 в прайсе»;
- правка — форма разворачивается под строкой (название, цена, период из пяти
  значений, описание, количество пользователей), а не отдельной страницей.
  «Сохранить» отправляет все пять полей, пустое описание и пустое количество
  пользователей уходят как `null`. На отправке кнопка неактивна и говорит
  «Сохраняем…»; отказ (`409`, `422`) показывается дословно над списком, форма
  остаётся развёрнутой, введённые значения не сбрасываются, а поле, которое
  назвал сервер, помечается `aria-invalid`;
- «Удалить» двухшаговое: первая кнопка заменяется парой «Подтвердить» /
  «Не надо», и только вторая пара отправляет `DELETE`. Строка **не исчезает**:
  `204` значит «снят с продажи», поэтому строка остаётся на месте с «Не в
  прайсе», а на месте «Удалить» появляется «Опубликовать» (`PATCH
  {"is_visible": true}` возвращает тариф в прайс);
- создания тарифа, назначения тарифа организации и правки `currency`,
  `unit_label`, `position`, `group_code`, `tooltip` на экране нет.

Каталог решений магазина (`/solutions`, макет `mockups/188/`):

- загрузка — «Загружаем решения…» в `role="status"`, счётчик не показывается;
- ошибка загрузки — текст `detail` дословно в `role="alert"` и кнопка
  «Повторить» рядом с ним (в том числе «Основной API недоступен» и «Кабинет не
  настроен: не задан OPERATOR_SERVICE_TOKEN»);
- пусто — «Решений пока нет»: строки каталога приходят из миграций базы, завести
  решение из кабинета нельзя;
- список: «Порядок», «Название», «Код», «Описание», «Цена», «Период»,
  «Состояние», «Создано», «Изменено», действия. Порядок строк — порядок ответа
  сервера (`position, id`): экран его не пересортировывает, потому что это и есть
  порядок карточек в магазине клиента. Цену печатает готовый `price_label`
  ответа — формулу цены экран не повторяет. Код показан целиком и не правится:
  это гейт платной функции. Счётчик в заголовке: «3 решения · 2 в каталоге»;
- правка — форма разворачивается под строкой: название, описание, порядок,
  состояние, цена, валюта, период из пяти значений. «Сохранить» отправляет все
  семь редактируемых полей, пустое описание уходит как `null`. После успешного
  `PATCH` экран перечитывает каталог (`GET /api/solutions`), поэтому правка
  «Порядка» сразу переносит строку на её новое место — место задаёт сервер, а не
  клиент. На отправке кнопка неактивна («Сохраняем…»), кнопки строки заперты;
  отказ (`409`, `422`) показывается дословно над списком, форма остаётся
  развёрнутой, введённые значения не сбрасываются, а поле, которое назвал
  сервер, помечается `aria-invalid` (`409` — всегда «Название»);
- «Удалить» двухшаговое: первая кнопка заменяется парой «Подтвердить» /
  «Не надо», и только «Подтвердить» отправляет `DELETE`. Строка **не исчезает**:
  `204` значит «снято с продажи», поэтому строка остаётся на месте с «Не в
  каталоге», а на месте «Удалить» появляется «Опубликовать» (`PATCH
  {"is_visible": true}` возвращает решение в каталог);
- фокус с клавиатуры возвращается в строку, когда нажатая кнопка исчезает из
  DOM: после «Подтвердить», после «Не надо» и после «Отмена»/«Сохранить»
  закрывшейся формы. Такая же правка сделана в прайсе тарифов (`/tariffs`);
- подпись под списком: снятие с продажи убирает карточку из магазина, и у
  организации с действующим правом пропадает пункт меню, хотя платная функция на
  сервере продолжает работать.

## Доступ на бою

Кабинет открыт на `https://operator.<SITE_DOMAIN>` — отдельным поддоменом того
же caddy, что обслуживает основной домен (`caddy/Caddyfile`):

```text
:443 ── TLS ── operator.<SITE_DOMAIN> ── reverse_proxy operator-web:80
                                            ├─ /      → SPA кабинета
                                            └─ /api/  → operator-api:8000 (nginx)
```

- Отдельный **хост**, а не путь на основном домене: cookie `operator_session`
  ставится host-only (`operator/backend/app/security.py`), и на своём поддомене
  она не пересекается с `crm_session` основного кабинета. Добавлять `domain=` к
  cookie не нужно и нельзя.
- Поддомен собирается из `SITE_DOMAIN` (`operator.{$SITE_DOMAIN}`) — отдельной
  переменной окружения нет намеренно: лишняя обязательная переменная роняет
  весь Caddyfile опечаткой, а вместе с ним и основной кабинет.
- HTTP на поддомене редиректится **на тот же хост** по HTTPS: имя входит в
  матчер `@ourhost` блока `:80`.
- Публикация на loopback (`OPERATOR_FRONTEND_PORT=127.0.0.1:8082`,
  `OPERATOR_API_PORT=127.0.0.1:8002`) остаётся как резерв для SSH-туннеля:
  `ssh -N -L 8082:127.0.0.1:8082 <сервер>`, дальше
  `http://localhost:8082/healthz`. Вход через домен и через туннель даёт **две
  разные сессии** — это ожидаемо (host-only cookie), а не баг.
- Проверки деплоя: шаг 16 требует `200 ok` на `https://operator.<домен>/healthz`
  и `200` на `https://operator.<домен>/api/health`. Подробности — `docs/ssl.md`.

**Пароль оператора — единственный слой защиты.** `basic_auth` на краю
сознательно не делаем, а в приложении нет ни ограничения попыток входа, ни
блокировки после N неудач. Поэтому `OPERATOR_PASSWORD` на бою обязан быть
длинным и случайным (не `change-me` и не словарный): это решение, а не
недосмотр. Публичный адрес — цена удобного доступа без туннеля.

## Чего здесь нет

- Создания организаций, удаления и архива: в API нет `DELETE`-семантики, а
  организация без владельца невидима никому.
- Поиска и фильтров по списку сверх постраничной выдачи; поиска по ИНН в DaData
  (все пять полей правятся руками); участников организации и приглашений.
- Создания тарифа, назначения тарифа организации из операторки, правки
  `currency`/`unit_label`/`position`/`group_code`/`tooltip` и аудита действий
  оператора. «Удаление» тарифа — это снятие с продажи: строку из базы оно не
  убирает (на неё ссылаются организации и счета), подписки доживают оплаченный
  период, лимит мест не меняется.
- Создания решения магазина и физического удаления строки каталога: за новой
  строкой в коде нет платной функции, а `code` — гейт права и `UNIQUE` в таблице,
  поэтому он только показывается и не правится. Период оплаты решения не правится
  тоже: у решения нет собственного срока, право действует, пока действует тариф
  организации (#195), и присланный `period` отвергается `422`. Выдачи и продления
  прав организации (`organization_solutions`) в кабинете нет; снятие активности
  расширения есть и **удаляет строку права** — после #195 запись «срок в прошлом»
  ничего не выключает, а платная функция живёт по тарифу. «Удаление» решения —
  снятие с продажи, как у тарифа.
- CORS и обмена с фронтендом основного кабинета (`app/frontend`): браузер
  кабинета ходит только в свой `operator-api` через nginx того же origin.
- Своей базы, alembic и миграций.
- Ролей, второго оператора, восстановления пароля, «запомнить меня», меню и
  других разделов кабинета.
- Видимости действий оператора в журнале основного кабинета: у строк
  платформенного контура нет организации, раздел «Журнал» читает по ней.
- Ограничения попыток входа, блокировки после N неудач и второго слоя защиты
  (`basic_auth` на краю не делаем намеренно — см. «Доступ на бою»).

# Ежедневный бэкап БД в S3

Резервная копия боевой PostgreSQL раз в сутки уезжает в S3-бакет под префиксом
`crm-prod`, последние 10 дампов хранятся там же, более старые удаляются
ротацией.

## Зачем это отдельно от деплоя

`.github/workflows/deploy.yml`, шаг 8, снимает `pg_dump -Fc` в
`/srv/crm-dormitory/backups/` **перед миграциями** — это страховка одного
события. У неё три дырки, которые закрывает этот runbook и
`.github/workflows/backup-db.yml`:

- дамп остаётся на том же сервере: диск, упавший вместе с базой, уносит и
  копию;
- ротации нет: каталог `backups/` копится, пока не кончится место;
- запуск привязан к релизу: если релизов нет месяц, нет и копий.

Шаг 8 при этом не отменяется и не меняется: страховка перед миграциями нужна
именно в момент миграции, а не в 03:00.

## Схема

```
GitHub Actions (cron 03:00 UTC)
  └─ ssh на сервер
       ├─ ОТДЕЛЬНЫЙ ШАГ: docker compose exec -T api python -m app.backup_cli check
       │       (S3 включён и префикс crm-prod — иначе job краснеет,
       │        а сервер ещё не тронут: ни дампа, ни локальной копии)
       ├─ docker compose ps -aq db            (имя контейнера не хардкодится)
       ├─ docker exec db pg_dump -Fc → /tmp/<дамп> в контейнере db
       ├─ docker cp → /srv/crm-dormitory/backups/<дамп>   (локальная копия)
       ├─ docker cp → /tmp/<дамп> в контейнере api
       ├─ docker compose exec -T api python -m app.backup_cli upload /tmp/<дамп> <дамп>
       ├─ docker compose exec -T api python -m app.backup_cli rotate backup/db 10
       └─ rm /tmp/<дамп> в контейнере; локальная копия удаляется только после успеха
```

`check` — отдельный шаг **до** дампа, а не внутри шага выгрузки. Поэтому его
отказ не оставляет после себя ничего: в `/srv/crm-dormitory/backups/` свежего
файла нет, и искать «локальную копию, которая осталась» не нужно.

S3-выгрузка идёт через `app/backend/app/storage.py` (`put_raw`, `list_folder`,
`delete`) — тот же слой, что и файлы кабинетов. Поэтому знание о бакете,
endpoint'е, подписи и префиксе среды живёт в одном месте, а не дублируется в
bash.

## Ключ объекта

Точный ключ в бакете:

```
crm-prod/backup/db/crm_<ГГГГММДД_ЧЧММСС>.dump
```

Пример: `crm-prod/backup/db/crm_20261103_030000.dump`.

- `crm-prod` — префикс боевой среды (`S3_ENV=prod`, `S3_PREFIX_PROD`);
- `backup/db/` — папка дампов, ротация работает только внутри неё;
- `crm_<ГГГГММДД_ЧЧММСС>.dump` — имя по UTC-времени снятия дампа. Шаблон
  `^crm_\d{8}_\d{6}\.dump$` — часть контракта между workflow и CLI: только
  такие объекты ротация считает дампами и удаляет.

Дампы лежат рядом с файлами пользователей (`crm-prod/<ГГГГ-ММ-ДД>/…`), но
ротация их не трогает: она отбирает только имена по шаблону и только прямо в
`backup/db/`.

## Секреты

Новых секретов GitHub нет — переиспользуются секреты деплоя:

| Секрет | Что это |
|---|---|
| `CRM_SSH_HOST` | адрес боевого сервера |
| `CRM_SSH_USER` | пользователь SSH |
| `CRM_SSH_PORT` | порт SSH (необязателен, по умолчанию 22) |
| `CRM_SSH_KEY` | приватный ключ доступа к серверу |

Ключей S3 в GitHub нет и не нужно: S3-конфигурация живёт в `.env` сервера, а
выгрузка выполняется **внутри контейнера `api`**, у которого уже есть и ключи,
и `boto3`.

## Расписание и ручной запуск

- Расписание: `cron "0 3 * * *"` — каждые сутки в 03:00 UTC (время GitHub
  Actions — UTC).
- **`schedule` срабатывает только с ветки по умолчанию (`main`).**
- **`workflow_dispatch` появляется там же.** GitHub показывает workflow в списке
  Actions (и кнопку «Run workflow») только для файла из ветки по умолчанию.
  Пока `.github/workflows/backup-db.yml` не слит в `main`, нет **ни расписания,
  ни кнопки** — проверять бэкап из рабочей ветки нельзя, файл туда ещё не
  доехал как запускаемый workflow.
- **Первый ручной прогон — после деплоя из `main`.** Запуск берёт файл workflow
  из ветки по умолчанию, а код CLI — из образа `api`, который на сервере уже
  собран. Если слить файл в `main` и запустить бэкап до деплоя, в образе ещё нет
  `app.backup_cli`, и job упадёт на шаге `check` с `No module named
  app.backup_cli`. Это не ошибка `.env` — сначала деплой (`deploy.yml` из
  `main`), потом бэкап.
- Порядок включения: merge `develop-m` → `main` → «Деплой на боевой сервер» из
  `main` → «Ежедневный бэкап БД» → «Run workflow» из `main`. После этого
  расписание работает само.
- Ручной запуск: Actions → «Ежедневный бэкап БД» → «Run workflow» → выбрать
  ветку. Отдельного гварда «только `main`» в файле нет: у бэкапа нет релизного
  смысла, гвард нужен был бы только чтобы запретить запуск из рабочей ветки —
  а такой запуск всё равно невозможен, пока файла нет в ветке по умолчанию.
- Одновременно выполняется один бэкап: `concurrency: crm-db-backup`,
  `cancel-in-progress: false`. Второй запуск ждёт первый, а не снимает
  параллельно второй дамп той же базы.

## Ротация и её необратимость

`rotate backup/db 10` оставляет 10 самых новых дампов по имени (формат
`crm_ГГГГММДД_ЧЧММСС` сортируется лексикографически в порядке времени),
остальные **удаляет безвозвратно**. Корзины в S3 нет: удалённый объект не
восстанавливается ничем, кроме собственной копии на другом носителе. Одиннадцатый
запуск вытесняет самый старый дамп — это нормальная работа, а не сбой.

`keep < 1` и папка вне `backup/` отвергаются кодом 1: «оставить ноль дампов» —
это не настройка, а удаление всех копий.

## Когда бэкап упал

Job краснеет, дамп в S3 за эти сутки не появляется. Порядок разбора:

1. Открыть Actions → «Ежедневный бэкап БД» → последний красный запуск, найти
   первый красный шаг.
2. Прочитать строку `ОШИБКА: …` — CLI и серверный скрипт печатают причину одной
   строкой без traceback.

| Что в логе | Что делать |
|---|---|
| «Не заданы секреты бэкапа» | Завести `CRM_SSH_*` в Settings → Secrets and variables → Actions (docs/deploy.md). |
| «хранилище — LocalStorage» | S3 выключен в `.env` сервера: пусты `S3_BUCKET` или ключи активной среды. Правится `.env` руками, workflow прод не меняет. |
| «префикс хранилища 'crm-agent-test'» | В `.env` сервера `S3_ENV=test`. Боевой дамп в тестовый префикс не пишется — поставить `S3_ENV=prod` и перезапустить. |
| `No module named app.backup_cli` | Образ `api` на сервере старше слияния в `main`. Сначала деплой из `main` (`deploy.yml`), потом бэкап. |
| «контейнер БД не найден» / «не запущен» | Стек на сервере не поднят. `cd /srv/crm-dormitory && docker compose up -d`, затем перезапуск бэкапа. |
| «S3: AccessDenied» / «нет связи с хранилищем» | Ключи S3 в `.env`, права на бакет, доступность `s3.twcstorage.ru`. |

**Локальная копия при сбое остаётся на сервере**, и её путь печатается в логе:

```
Локальная копия осталась на сервере: /srv/crm-dormitory/backups/crm_<TS>.dump
```

Она удаляется только после успешной выгрузки и ротации, поэтому после
красного прогона её нужно или использовать для восстановления, или забрать с
сервера как есть. `/tmp` внутри контейнеров `db` и `api` чистит `trap on_exit`
— и на ошибке, и на обычном выходе. Если job убит по `timeout-minutes` или
отменён вручную из интерфейса, `trap` не выполнится и дамп останется в `/tmp`
контейнера: это мусор, а не поломка — имя содержит секунды, следующая копия его
не перепутает, а том `/tmp` живёт до пересоздания контейнера.

## Восстановление из S3

Скачать объект `crm-prod/backup/db/crm_<TS>.dump` из бакета на сервер (в
каталог `/srv/crm-dormitory/backups/`), затем — как в `docs/deploy.md`, раздел
«Откат»:

```bash
# на сервере, в /srv/crm-dormitory
docker compose --profile tls stop api bot
DB="$(docker compose ps -q db)"
DB_USER="$(docker exec "$DB" printenv POSTGRES_USER)"
DB_NAME="$(docker exec "$DB" printenv POSTGRES_DB)"
docker cp /srv/crm-dormitory/backups/crm_<TS>.dump "$DB":/tmp/restore.dump
docker exec "$DB" pg_restore -U "$DB_USER" -d "$DB_NAME" --clean --if-exists /tmp/restore.dump
docker exec "$DB" rm -f /tmp/restore.dump
```

Дамп снят с `-Fc`, поэтому восстанавливается только `pg_restore`, а не `psql`.
`--clean --if-exists` сносит существующие объекты перед восстановлением: база
возвращается ровно к состоянию на момент дампа. Поднимать `api` и `bot` после
восстановления — повторным деплоем из `main`, иначе `alembic upgrade head`
вернёт схему, от которой вы только что откатились (docs/deploy.md).

Проверка, что дамп живой: внутри восстановленной базы есть таблица
`alembic_version` с номером ревизии.

## Персональные данные

Дамп содержит персональные данные жильцов, поэтому:

- бакет обязан быть **непубличным**: ни публичного доступа к бакету, ни
  публичных ссылок на объекты. Ключи S3 — только в `.env` сервера;
- объекты под `backup/db/` не публикуются и не раздаются через API;
- дамп читается в память целиком (`backup_cli upload`), поэтому потолок размера
  базы — память контейнера `api`;
- дамп не архивируется дальше и не выкладывается в сторонние сервисы.

## Чего здесь нет

- **Уведомлений о падении нет.** О красном прогоне узнают только из Actions —
  отдельного сообщения в Telegram или на почту эта задача не шлёт.
- Lifecycle-политики бакета нет: ротацией управляет `rotate`, а не S3.
- Тома `uploads` в бэкап не входят: файлы пользователей живут в S3 отдельно и
  архивированием базы не покрываются.
- Ни `schedule`, ни `workflow_dispatch` не работают до слияния `develop-m` →
  `main`; первый ручной прогон — только после деплоя из `main` (см. «Расписание
  и ручной запуск»).

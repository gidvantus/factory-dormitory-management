# Файловое хранилище и доступ к файлам

Файлы проекта проходят через один модуль — `app/backend/app/storage.py`. Других
путей к файлам в приложении нет: ни ручек вида «положи файл», ни прямых
`open()`/`Path.write_bytes()` в доменном коде.

## Хранение: S3 или локальный диск

Режим выбирается настройками (`app/backend/app/config.py`), а не сборкой образа:

| Условие | Режим | Где лежат файлы |
|---|---|---|
| заданы `S3_ENDPOINT`, `S3_BUCKET` и ключи активной среды | `S3Storage` | бакет Timeweb Cloud под префиксом среды |
| что-то из этого пусто | `LocalStorage` | каталог `app/backend/uploads` (в контейнере `/app/uploads`) |

Среда выбирается `S3_ENV=test|prod`: `test` берёт пару `S3_ACCESS_KEY_TEST` /
`S3_SECRET_KEY_TEST` и префикс `crm-agent-test`, `prod` — `S3_ACCESS_KEY_PROD` /
`S3_SECRET_KEY_PROD` и префикс `crm-prod`. Регион подписи — `ru-1`.

**Ключи доступа кладутся только в `.env`** (он в `.gitignore`). В репозитории
есть только имена переменных с пустыми значениями — `.env.example`. Ключи не
логируются: в лог уходит причина отказа хранилища, но не значения доступа.

Внутри префикса (или каталога) файлы раскладываются по дням UTC:

```
crm-agent-test/2026-10-29/8f14e45fceea167a5a36dedd4bea2543.xlsx
uploads/2026-10-29/8f14e45fceea167a5a36dedd4bea2543.xlsx        (без S3)
```

Ключ хранилища — часть пути **после** префикса среды: `2026-10-29/<uuid>.xlsx`.
Его возвращает `storage.save_bytes(...)`, его же принимают `read_bytes`,
`delete`, `exists`. Путь в API пишется с префиксом `uploads/`
(`app/file_access.stored_path`), а в ссылке `file_url` — как `/uploads/<ключ>`.

Имя объекта делает сервер, а не клиент: `.xlsx` импорта получает
`uuid4().hex + ".xlsx"`. Имя файла из запроса (`filename`) сохраняется отдельно,
в `import_jobs.filename`, и в ключ хранилища не попадает.

Ключ проверяется на обход каталогов: пустой ключ, абсолютный путь и любая часть
`..` (а также `.` и пустые части) отклоняются с `StorageError`. `boto3`
импортируется лениво — режим локального диска работает без него.

## Раздача: `GET /uploads/{key}`

Маршрут живёт в `app/main.py` **вне** `/api` и публикуется в OpenAPI. nginx
(`app/frontend/nginx.conf`) проксирует `/uploads/` на тот же api, поэтому ссылка
открывается тем же origin, что и SPA, и cookie сессии `crm_session` (`path=/`)
уходит сама — отдельной медиа-cookie не нужно.

| Ситуация | Ответ |
|---|---|
| аноним (нет cookie сессии) | `404` `{"detail": "Файл не найден"}` |
| вошедший, но файл не его организации | `403` `{"detail": "Нет доступа к файлу"}` |
| участник организации-владельца | `200`, байты файла |
| пустой ключ, ключ с `..`, ключа нет ни у одного задания | `404` «Файл не найден» |
| ключ есть в задании, объекта в хранилище нет | `404` «Файл не найден» |

Аноним не узнаёт, существует ли файл: `404` — единственный его ответ. Тексты
отказов — часть контракта для клиента; фронт их не показывает и не переписывает
(отказ скачивания рисует браузер).

Заголовки ответа `200`:

- `Content-Type` — по расширению ключа (`app/file_access.content_type_for`:
  небольшая таблица плюс `mimetypes.guess_type`; таблица нужна потому, что в
  slim-образе нет `/etc/mime.types` и `.xlsx` иначе уходил бы как
  `application/octet-stream`); неизвестное расширение — `application/octet-stream`;
- `X-Content-Type-Options: nosniff` и `Content-Security-Policy: default-src
  'none'; sandbox` — загруженный файл при открытии по прямой ссылке не должен
  исполнить скрипт на нашем origin;
- `Cache-Control: private, no-store` — копия закрытого файла не должна пережить
  отзыв доступа ни в браузере, ни в общем прокси. `Vary` не нужен: ответ и так
  не кэшируется;
- `Content-Disposition` **не** ставится: ссылка открывает файл, а не навязывает
  имя.

## Правила доступа

Правило одно и живёт в `app/file_access.can_read`:

> файл читает участник организации, которой принадлежит общежитие задания
> импорта с этим `file_key`.

То есть право даёт **привязка файла к данным**, а не факт загрузки:

- `import_jobs.file_key` — единственная связь файла с данными в CRM. Задание
  знает своё общежитие, общежитие знает организацию
  (`dormitories.organization_id`) — по этой цепочке и считается доступ;
- членство проверяется явно (строка `organization_members`), а не только
  `users.active_organization_id`: ссылка на организацию без строки членства
  правом не является;
- реестр загрузок `uploaded_file` (`uploader_kind`, `uploader_id`, `purpose`) —
  это **учёт и диагностика**, а не право. Иначе сотрудник, загрузивший импорт,
  был бы единственным, кто может его скачать, а коллеги по организации получали
  бы `403`;
- публичных файлов (логотипов, картинок), владельческого правила, чатов и
  аватаров в CRM нет. Заводить их «на будущее» не нужно: без явного правила
  файл закрыт всем, и это безопасное состояние по умолчанию.

Участник организации без нужных прав доступа к разделу файл всё равно читает:
это чтение своих данных, роль значения не важна. Пробный период и блокировка
кабинета скачивание не ограничивают — файл уже загружен и принадлежит
организации.

## Реестр загрузок `uploaded_file`

Ревизия `0053_uploaded_files`:

| Колонка | Смысл |
|---|---|
| `id` | первичный ключ |
| `key` | ключ хранилища без префикса `uploads/`, уникальный индекс |
| `uploader_kind` | тип аккаунта загрузившего; в CRM он один — `user`, `NULL` — служебная загрузка |
| `uploader_id` | идентификатор пользователя (индекс) |
| `purpose` | назначение загрузки (`places_import` и появляющиеся виды файлов) |
| `created_at` | момент загрузки, с часовым поясом |

Повторная регистрация того же ключа ничего не меняет: первая запись остаётся.
`register_upload(..., commit=False)` пишет регистрацию в общую транзакцию
вызывающего кода — так импорт сохраняет файл, задание и строку реестра одним
коммитом.

## Как добавить новый вид файлов

1. Сохранить файл через `storage.save_bytes(...)` (или `storage.put_raw(...)`,
   если раскладка по дням не подходит) и вызвать
   `register_upload(session, key, user, purpose="...")`.
2. Связать ключ с данными организации — колонкой `file_key` (или её аналогом) в
   таблице, которая уже знает свою организацию. **Без такой связи файл не
   прочитает никто**: это и есть поведение по умолчанию.
3. Добавить явное правило в `app/file_access.can_read` и тест на него в
   `app/backend/tests/test_file_access.py`.
4. Отдавать файл клиенту только через `/uploads/{key}` — других путей к файлам
   быть не должно.
5. Если файл появляется в ответе API, отдать готовый адрес
   `/uploads/<ключ>` (как `file_url` у импорта), а не ключ: клиент не должен
   собирать адрес сам.

## Эксплуатация

**Том.** В режиме без S3 каталог `/app/uploads` смонтирован томом `uploads`
(сервис `api` в `docker-compose.yml`). Без тома файлы исчезали бы при каждой
пересборке контейнера. Проверить режим на стенде:

```bash
docker compose exec api python -c "from app.storage import storage; print(type(storage).__name__)"
```

`S3Storage` — ключи заданы, `LocalStorage` — режим локального диска.

**Уборки нет.** У файлов нет срока хранения и нет чистки: бакет растёт вместе с
числом импортов, как растёт таблица `import_jobs`. Квоты, сроки хранения и
антивирусная проверка в задачу не входили.

**Удаление общежития.** `import_jobs` уходит каскадом (`ON DELETE CASCADE`), а
файл в бакете остаётся, но становится недоступным: связь «файл → задание → общежитие»
исчезла, и правило доступа не находит организацию. Это принято: удаление
общежития не чистит хранилище, а осиротевший объект не открывается никому.

**Откат ревизии.** `alembic downgrade -1` снимает `import_jobs.file_key` и таблицу
`uploaded_file`: задания импорта теряют ссылки на файлы, а сами объекты в бакете
остаются недоступными. Обратно они становятся доступными только вместе с
записями `import_jobs`.

# HTTPS, домен и сертификат (Let's Encrypt через Caddy)

Боевой стенд отдаётся наружу по HTTPS. TLS терминирует контейнер **caddy**
(корневой `docker-compose.yml`, профиль `tls`), он же получает и продлевает
сертификаты Let's Encrypt. На хосте ничего не устанавливается: nginx и certbot
на сервере не нужны, конфигурация живёт в репозитории (`caddy/Caddyfile`).

## Как устроено

```text
интернет
  │
  ├─ :80  ── acme-челлендж (Caddy обслуживает сам)
  │       ── /healthz → 200 «ok» без редиректа
  │       ── всё остальное → 301 на https://<домен>/…
  │
  └─ :443 ── TLS (сертификат Let's Encrypt)
          └─ reverse_proxy web:80 ── nginx фронта
                                     ├─ /      → SPA
                                     └─ /api/  → api:8000
```

- Caddy выпускает сертификат на `SITE_DOMAIN` и `www.SITE_DOMAIN` сам, там же
  его и продлевает (за 30 дней до истечения). Аккаунт ACME и сертификаты лежат
  в томе `caddy_data` и переживают пересборку контейнера.
- API проксируется с того же origin, что и SPA: `/api/` уводит на `api:8000`
  nginx фронта (`app/frontend/nginx.conf`), поэтому CORS и второй домен для API
  не нужны — `Access-Control-Allow-Origin` в API выключен намеренно.
- Локально профиль `tls` не поднимается: `docker compose up -d` не создаёт
  `caddy`, стенд разработчика работает как раньше и порты `FRONTEND_PORT` /
  `API_PORT` не меняются.

## Домен

- Домен **не вписан в `Caddyfile`**: он приходит из `.env` (`SITE_DOMAIN`) и
  подставляется в конфиг при старте контейнера. Один и тот же файл работает для
  любого домена, а в репозитории нет значения, которое пришлось бы менять перед
  каждым деплоем.
- `SITE_DOMAIN` — только имя: без схемы, без пути и без `www`. `www`-вариант
  Caddyfile добавляет сам (`www.{$SITE_DOMAIN}`), сертификат выпускается на оба
  имени сразу.
- Запросы по нашему домену (в том числе `www`) редиректятся на тот же хост по
  HTTPS. Запросы по IP или чужому `Host` уходят на канонический
  `https://<домен>`: сертификата на IP-адрес не существует, и без этого
  редиректа браузер показывал бы «Подключение не защищено» уже после перехода
  на HTTPS.
- Если `SITE_DOMAIN` пуст, Caddyfile в этом месте не собирается и контейнер не
  стартует. Это защита от случайного запуска ACME без домена, а не дефект.

## DNS

Нужна **одна A-запись** на адрес сервера и `www` на тот же адрес:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| A | `@` (или пусто) | адрес сервера | 600 |
| A | `www` | адрес сервера | 600 |

Правила:

- **AAAA-записи быть не должно** — если у сервера нет IPv6, лишняя запись ломает
  валидацию Let's Encrypt;
- не включать прокси/CDN: ACME нужен прямой ответ сервера на портах 80 и 443;
- проверка резолва: `nslookup <домен>` → адрес сервера. Кириллицу `nslookup` не
  понимает — имя надо проверять в punycode (`xn--…`), в таком же виде оно
  попадает в `SITE_DOMAIN`, если домен кириллический.

## `.env` на сервере

`.env` правится руками на сервере и деплоем не перезаписывается. Для HTTPS
нужны строки:

| Переменная | Значение | Зачем |
|---|---|---|
| `SITE_DOMAIN` | `<домен>` (без схемы и без `www`) | домен, на который выпускается сертификат |
| `ACME_EMAIL` | адрес почты в ASCII | письма об истечении сертификата от Let's Encrypt |
| `CADDY_ACME_CA` | `https://acme-v02.api.letsencrypt.org/directory` | боевая ACME-директория (staging — только для первой проверки) |
| `FRONTEND_PORT` | `127.0.0.1:8081` | **обязательно**: порт 80 нужен caddy, иначе `bind: address already in use` |
| `API_PORT` | `127.0.0.1:8001` | **обязательно**: иначе API остаётся опубликованным на всех интерфейсах в обход TLS (`http://<ip>:8001`), и пароль с cookie сессии ходят открытым текстом |
| `FRONTEND_BASE_URL` | `https://<домен>` | из него собирается ссылка активации в письме, иначе она остаётся `http://localhost:8080` |
| `SESSION_COOKIE_SECURE` | `true` | cookie сессии `crm_session` отдаётся только по https |

`FRONTEND_PORT=127.0.0.1:8081` публикует фронт только на локальный адрес
сервера — для отладки и проверок с самого сервера. Наружу его больше не
публикуем: снаружи всё идёт через caddy.

`API_PORT=127.0.0.1:8001` закрывает то же самое для API: по умолчанию compose
публикует его на всех интерфейсах (`"${API_PORT:-8001}:8000"`), и без этой
строки защищённый домен даёт второй, открытый вход в обход TLS — снаружи он
доступен любому сканеру портов. Caddy проксирует API внутри сети проекта
(`web` → `api:8000`), публикация на хост ему не нужна. На локальном стенде
`API_PORT` остаётся как был: это настройка сервера.

В `.env.example` в репозитории эти значения не включены намеренно:
`FRONTEND_PORT` по умолчанию `8080`, `SESSION_COOKIE_SECURE` — `false`, а
`SITE_DOMAIN` и `ACME_EMAIL` пусты. Это настройки сервера, а не локального
стенда.

## Запуск и первый выпуск сертификата

На сервере, в каталоге проекта:

```bash
docker compose --profile tls up -d --build
```

**Первый выпуск делать на staging**, иначе неудачные попытки съедают лимиты
Let's Encrypt (5 неудачных валидаций в час на домен):

1. в `.env`: `CADDY_ACME_CA=https://acme-staging-v02.api.letsencrypt.org/directory`;
2. `docker compose --profile tls up -d --force-recreate caddy`;
3. убедиться, что сертификат выпущен (браузер на staging покажет
   предупреждение — это ожидаемо):

   ```bash
   docker logs <caddy-контейнер> --tail 30 | grep -i "certificate obtained"
   ```

4. вернуть боевой ACME (`https://acme-v02.api.letsencrypt.org/directory`) и
   пересоздать контейнер:

   ```bash
   docker compose --profile tls up -d --force-recreate caddy
   ```

Дальше продление автоматическое. Том `caddy_data` **удалять нельзя**: вместе с
ним уходят аккаунт ACME и сертификаты, а новый аккаунт упирается в лимиты.

## Проверка

С сервера (обращение к 127.0.0.1, но с настоящим `Host`/SNI домена):

```bash
curl -s -o /dev/null -w '%{http_code}\n' --resolve <домен>:443:127.0.0.1 https://<домен>/healthz   # 200
curl -s -o /dev/null -w '%{http_code}\n' --resolve <домен>:443:127.0.0.1 https://<домен>/api/health # 200
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/healthz                                  # 200 (без редиректа!)
curl -sI http://<домен>/ | head -1                                                                 # 301 → https
```

Срок и издатель сертификата:

```bash
echo | openssl s_client -connect <домен>:443 -servername <домен> 2>/dev/null | openssl x509 -noout -issuer -dates
```

Конфиг внутри контейнера без перезапуска:

```bash
docker logs <caddy-контейнер> --tail 50
docker exec <caddy-контейнер> caddy validate --config /etc/caddy/Caddyfile
docker exec <caddy-контейнер> caddy reload --config /etc/caddy/Caddyfile
```

## Как добавить ещё домен

1. A-запись на адрес сервера (AAAA — нет);
2. блок в `caddy/Caddyfile`:
   `example.ru { reverse_proxy <сервис>:<порт> }`;
3. применить конфиг: `docker exec <caddy-контейнер> caddy reload --config /etc/caddy/Caddyfile`
   — сертификат выпустится автоматически.

## Почему каталог `caddy/`, а не один файл

В compose примонтирован каталог (`./caddy:/etc/caddy:ro`). Если примонтировать
отдельный файл и заменить его снаружи, bind-mount продолжает указывать на старый
inode, и контейнер видит прежнюю версию — правки не применяются. С каталогом
конфиг всегда актуальный. Кроме того, работающий Caddy держит конфиг в памяти:
после обновления файла нужен `caddy reload` (или
`docker compose --profile tls up -d --force-recreate caddy`).

## Откат на HTTP

```bash
# на сервере
docker compose --profile tls stop caddy
# в .env: FRONTEND_PORT=80
# в .env: SESSION_COOKIE_SECURE=false, FRONTEND_BASE_URL=http://<адрес>
docker compose up -d web
```

Две последние строки обязательны вместе с откатом: при `SESSION_COOKIE_SECURE=true`
API отдаёт `Set-Cookie: crm_session=…; Secure` (`app/backend/app/security.py`), и
браузер по `http://` такую cookie выбрасывает — кабинет будет бесконечно просить
вход; а `FRONTEND_BASE_URL=https://<домен>` отправляет в письме ссылку активации
на домен, которого при откате больше нет. При повторном включении TLS оба
значения возвращают: `SESSION_COOKIE_SECURE=true`, `FRONTEND_BASE_URL=https://<домен>`.

Стенд снова доступен по `http://<адрес>:80` без TLS, как до внедрения. Том
`caddy_data` при откате не удаляется: сертификаты дождутся следующего включения.

## Частые причины сбоя

| Симптом | Причина |
|---|---|
| `bind: address already in use` в логах caddy | порт 80/443 занят: в `.env` не выставлен `FRONTEND_PORT=127.0.0.1:8081` |
| `http://<ip>:8001/api/…` открывается снаружи, в обход домена | в `.env` не выставлен `API_PORT=127.0.0.1:8001`: API опубликован на всех интерфейсах |
| сертификат не выпускается | нет A-записи, есть лишняя AAAA, закрыт порт 80/443 у провайдера, DNS ещё не разошёлся |
| в браузере «не защищено» | выпущен staging-сертификат (вернуть боевой `CADDY_ACME_CA` и пересоздать caddy); сертификат при этом валиден |
| `/healthz` отвечает не 200 | сломан блок `:80` в `caddy/Caddyfile` — он обязан отдавать 200 без редиректа |
| правки `Caddyfile` не применяются | конфиг не перечитан: `caddy reload`; если не помогло — `--force-recreate caddy` |
| `http://<IP>` ведёт на `https://<IP>`, браузер ругается | в блоке `:80` нет редиректа неизвестных хостов на канонический домен |
| сайт отдаёт 502 | упал контейнер `web` в сети проекта |
| caddy не стартует, в логах пустой адрес | не задан `SITE_DOMAIN` в `.env` |

Логи: `docker logs <caddy-контейнер> --tail 100`.

## Порты 80/443 на сервере Vahta

Порты 80 и 443 на сервере проекта Vahta уже заняты её собственным caddy.
CRMDormitory нужен **отдельный сервер** (или отдельная цепочка прокси перед
ним): второй контейнер caddy с теми же портами на той же машине не поднимется.
Адрес сервера и домен выбирает человек; в репозитории их нет.

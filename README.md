# CRM Dormitory

Проект для учёта рабочих на общежитиях.

## Назначение

CRM-система ведёт учёт рабочих, проживающих в общежитиях: заселение и выселение,
распределение по комнатам и местам, кадровые и бытовые данные. Система нужна
комендантам и кадровой службе, чтобы видеть актуальную занятость мест и историю
проживания.

## Возможности

- реестр рабочих: карточка, подразделение, статус;
- реестр общежитий: здания, комнаты, места;
- заселение, переселение и выселение с историей;
- отчётность по занятости мест.

В разделе «Общежития» уже доступны создание (название общежития и клиента),
карточки с клиентом перед названием и переход внутрь общежития. Данные сохраняются
в PostgreSQL. Пока все вошедшие пользователи видят общий список; разграничение
доступа будет добавлено вместе с ролями и правами. Создатель записывается для учёта
авторства.

Название общежития и клиента можно изменить кнопкой «Редактировать» на карточке.
«В архив» меняет статус без удаления данных: карточка становится
тусклой с пометкой «Архив», данные продолжают участвовать во всех расчётах дашборда.
«Восстановить» возвращает активный статус. Доступ к таблицам архивного общежития сохраняется.
Архивные карточки отображаются после активных; кнопки управления находятся только на карточках.

В таблицах «Проживающие», «Приток», «Отток», «На аванс», «На расчёт» и «Архив»
доступны кнопки «Добавить столбец» и «Настроить столбцы». Для нового столбца
выбирается текст, число, дата, чекбокс или выпадающий список с вариантами.
Настройки сохраняются отдельно для каждого общежития и таблицы. Столбцы можно
переименовать, удалить из таблицы и восстановить вместе с данными. Тип после
создания неизменяемый; использованные варианты списка можно архивировать.

В «Проживающих» кнопки «Записать» на аванс и расчёт копируют значения в соответствующий
список выплат в том же общежитии. Сравниваются текущие названия и типы всех действующих
столбцов, включая добавленные пользователем; регистр и лишние пробелы не учитываются.
Удалённые столбцы и служебные кнопки пропускаются. Варианты выпадающих списков
сопоставляются по названию. Поля без пары остаются пустыми; о несовместимых значениях
показывается сообщение. Кнопка дожидается сохранения ячеек строки. Проживающий остаётся
в исходном списке, а данные выплаты сохраняются отдельно и не меняются вслед за ним.
Повторная запись того же проживающего в тот же список не создаёт дубликат и не затирает
выплату; также проверяется совпадение табельного номера с существующими выплатами.
После удаления выплаты или очистки списка можно записать проживающего снова.
Кнопка «Перевести» в «Проживающих» открывает выбор другого активного общежития.
До переноса сравниваются текущие столбцы двух таблиц: названия, типы и выбранные
варианты списков. Совпадающие данные переносятся с новыми идентификаторами
пользовательских столбцов и вариантов; хостел сопоставляется по названию среди
действующих в текущем месяце. Если поле отсутствует, удалено или несовместимо,
показывается причина и требуется подтверждение перевода без этого поля.
Заполненные скрытые столбцы также перечисляются перед потерей данных.
При изменении строки или столбцов после сравнения требуется повторная проверка.
Перевод атомарно перемещает одну строку, сохраняя её идентификатор; аванс и расчёт
остаются в исходном общежитии. Если в получателе уже есть такой Т/н, перевод блокируется.

Кнопка «Отток» сравнивает текущие столбцы «Проживающих» и «Оттока» этого общежития
по названию и типу, включая пользовательские столбцы. Окно содержит только подтверждение
переноса и удаления исходных записей, без списка полей и отдельного подтверждения потерь.
Совпадающие данные переносятся автоматически; дата выезда копируется только из
совпадающего столбца и иначе остаётся пустой. При удалении записей на аванс и расчёт
учитываются связанные с проживающим записи и ручные строки с тем же Т/н, за все даты
в этом общежитии. Записи, связанные с другим проживающим, не удаляются.
Создание оттока, удаление проживающего и его выплат выполняются одной транзакцией.
Если после сравнения менялись данные, столбцы или выплаты, требуется новое сравнение.
Миграция `0013_resident_payments` добавляет связь для проверки повторной записи;
существующие выплаты сохраняются. Удаление проживающего сохраняет данные его выплат.

В «На аванс» и «На расчёт» кнопка «Очистить список» удаляет все строки выбранной
подвкладки в текущем общежитии после подтверждения, включая записи вне выбранного
периода. Столбцы и другие списки сохраняются. При ошибке список остаётся на экране,
очистку можно повторить.

Пользовательская вкладка при создании получает собственные настройки: обычная таблица
или ручная таблица с датами в столбцах, без периода / диапазон / месяц, кнопки
«Добавить строку», «Очистить список» и действия удаления строки. В обычной таблице
период фильтрует записи по выбранному столбцу типа «Дата» (включая обе границы;
строки без даты исключаются). При создании вкладки с периодом столбец «Дата»
добавляется автоматически. Видимость столбцов дат можно отключить отдельно.
В формате с датами в столбцах все строки сохраняются между месяцами, значения
вводятся вручную по дням. Формулы и связи общего отчёта этим форматом не добавляются.
Настройки доступны и в «Настроить»: переключение формата и отключение кнопок
не удаляют строки, обычные ячейки и дневные значения. Очистка после подтверждения
удаляет весь список за всё время. Шаблоны копируют возможности и структуру с новыми
ID столбцов, без записей. Миграция `0040_custom_tab_options` сохраняет прежнее
поведение существующих вкладок по умолчанию.

В «Общем отчёте» доступны ручные, формульные и связанные строки. Для связи
выбираются раздел, подвкладка, столбец и условие: «Равно выбранному значению»
или «Заполнено — любое значение». Каждая подходящая запись даёт 1. При выборе
столбца с датой по умолчанию считаются все заполненные даты с распределением
по этому же столбцу. Для остальных столбцов количество распределяется по дате создания записи в часовом
поясе Europe/Moscow; можно выбрать столбец с датой события. Записи с пустой датой
события пропускаются. Пустой результат даёт 0, нарушенная связь — ошибку.
Расчёт выполняется при загрузке отчёта, поэтому изменения и удаления источника
учитываются при следующем открытии или обновлении отчёта. Связанные строки можно
использовать в формулах; их ячейки не редактируются вручную. Удаление столбца,
на который ссылается отчёт, блокируется с указанием зависимых строк.

Шаблон отчёта переносит формулы, связи и структуру таблиц-источников в новое
общежитие с новыми идентификаторами столбцов, без записей и значений ячеек.
«Архив» содержит отдельные записи с настраиваемыми столбцами; автоматического
переноса проживающих в него пока нет.

Во вкладке «Размещение персонала» свободные места рассчитываются автоматически за каждый день
и хостел: оплачено мест минус проживает, отдельно для М и Ж. Итог свободных мест
складывает оба результата. При изменении или очистке исходных ячеек расчёт
обновляется после автосохранения. Пустое исходное значение считается нулём;
если обе исходные ячейки пусты, результат остаётся пустым. Отрицательная разница
отображается без округления до нуля. Ручное редактирование свободных мест закрыто;
ранее сохранённые ручные значения сохраняются в базе и заменяются расчётом при выводе.

Во вкладке «Размещение персонала» есть импорт из Excel. Кнопка «Импорт из Excel» стоит в шапке
хостела рядом с «Убрать»: импорт открывают из строки того хостела, с которым
работают. В окне скачивают шаблон за выбранный месяц, заполняют его и загружают
обратно.
Шаблон повторяет экран: каждый хостел занимает четыре строки — «Проживает М»,
«Проживает Ж», «Оплачено мест М», «Оплачено мест Ж», — а дни идут колонками.
Лист защищён от добавления и удаления строк и колонок, числовые ячейки принимают
целое от 0 до 1 000 000 000; «Итого» и «Свободных мест» в шаблон не входят.
Разбор показывает ошибки с номером строки и названием колонки и предупреждения,
а в базу пишет только после кнопки «Применить импорт». Месяц из файла заменяется
целиком: значения из файла записываются, пустая ячейка удаляет значение, а остальные
месяцы не меняются. Шаблон отдаёт
`GET /api/dormitories/{id}/hostels/import/template?month=2026-01-01`, разбор —
`POST /api/dormitories/{id}/hostels/import` (multipart, поле `file`, до 20 МБ),
применение — `POST /api/dormitories/{id}/hostels/import/{import_id}/confirm`.

Уведомления в Telegram — отдельное платное решение магазина улучшений: подключаются
из кабинета, но только при действующем праве организации. Настройки живут на
странице «Уведомления» (`/cabinet/notifications`), пункт меню появляется вместе с
правом. Кнопка «Подключить Telegram» выдаёт одноразовый код и ссылку на бота —
имя бота знает только сервер, фронт его не подставляет. Код живёт 15 минут и
лежит в базе только хешем; после `/start
<код>` бот связывает чат с учётной записью, и карточка сама показывает
«Подключено» (статус переспрашивается раз в 5 секунд, пока чат не подключён).
Первое событие — выселение проживающего: сообщение получают коллеги по
организации с подключённым Telegram и действующим правом, сам выселяющий — нет.
Уведомление не входит
в транзакцию оттока: падение рассылки не откатывает выселение, а одно и то же
событие не создаёт второй доставки. Рассылку забирает отдельный сервис `bot` на
том же образе (`python -m app.bot`). Публичного вебхука нет: наружу не открыт ни
один роут, бот сам ходит в Bot API. Токен бота (`TELEGRAM_BOT_TOKEN`) и служебный
секрет `TELEGRAM_SERVICE_TOKEN` живут только в окружении; пока токен пуст,
приложение работает как раньше, а подключение отвечает 503. Ручки кабинета —
`GET /api/telegram/status`, `POST /api/telegram/connect`,
`POST /api/telegram/disconnect`, `PATCH /api/telegram/subscriptions`,
`POST /api/telegram/test-message`; ручки бота (заголовок `X-Bot-Token`) —
`POST /api/telegram/chat`, `GET /api/telegram/chats`,
`GET /api/telegram/feed?chat_id=…`, `POST /api/telegram/feed/{id}/failed`.
Готовое уведомление адресовано человеку, а не ответу на его сообщение, поэтому
бот обходит `GET /api/telegram/chats` и забирает ленту каждого подключённого
чата — иначе доставка ждала бы, пока получатель сам напишет боту. Миграция
`0032_telegram_notifications` добавляет три таблицы и новый вид одноразовой
ссылки `telegram_link`; данные пользователей не затрагиваются.

### Магазин улучшений

Магазин (`/cabinet/shop`) продаёт решения — отдельные функции поверх тарифа.
Решение не заменяет тариф: тариф держит кабинет живым целиком, а право на решение
открывает одну функцию. Раздел виден всегда, в том числе на закрытом пробном
кабинете: покупка нужна именно там. В боковом меню «Магазин улучшений» стоит после
«Статистики», а разделы купленных решений идут сразу за ним: новый пункт меню
появляется после магазина, а не в середине списка.

Право принадлежит **организации**, а не человеку: купил владелец — пользуются все
участники. Строка каталога задаёт цену и период (`month`, `half_year`, `year`,
`once`), из периода в момент оплаты считается `expires_at`. `once` даёт
бессрочное право (`expires_at IS NULL`). Периоды — календарные месяцы с усечением
на конце месяца: 31 января плюс месяц — 28 или 29 февраля. Продление правит ту же
строку права и считает новый срок от `max(сейчас, текущий срок)`: неоплаченное
время не сгорает.

Покупка идёт **существующим счётом**: `POST /api/billing/invoices` с
`solution_id` (тариф — с `tariff_id`; ровно одно из двух полей, иначе 422). Счёт
хранит вид предмета в `item_kind` (`tariff` или `solution`), а снимок названия и
периода — в прежних колонках `tariff_name`/`tariff_period`, поэтому вид предмета
печатную форму не меняет. Счёт и акт скачиваются **PDF-файлами** с прежних
адресов (`GET /api/billing/invoices/{id}/file` и `.../act-file`): форма
собирается в памяти и уходит вложением, на диск ничего не пишется, а кириллицу
несёт встроенный шрифт из образа API. Живой неоплаченный счёт дедуплицируется по
предмету: счёт за тариф и счёт за решение друг другу не мешают. Оплата (`PATCH`
со статусом `paid`) выдаёт или продлевает право и заводит акт; тариф организации
при этом не меняется. Каталог отдаёт `GET /api/solutions`: цена приходит готовой
строкой (`price_label`), фронт её не считает.

По окончании периода право перестаёт действовать: `GET /api/solutions` отдаёт
`is_owned = false`, пункт «Уведомления» исчезает, страница `/cabinet/notifications`
показывает «Решение не подключено» со ссылкой в магазин, а ручки платной функции
отвечают 403. Строки `telegram_links` при этом не удаляются и не отзываются:
очередь доставок — состояние базы, а не права.

Каталог задаётся данными: миграция `0035_solutions` заводит две таблицы
(`solutions`, `organization_solutions`), две колонки счёта (`solution_id`,
`item_kind`) и ровно одно решение — `telegram_notifications` («Уведомления в
Telegram», 500 ₽ в месяц). Откат убирает обе таблицы и обе колонки, не трогая
прежние счета и тарифы.

Миграция `0011_table_columns_links` добавляет настройки и дополнительные поля,
сохраняя существующие записи. При запуске API миграции применяются автоматически.

## Доступ к данным: организация у общежития

Данные кабинета принадлежат организации, и точка правды о принадлежности **одна** —
колонка `dormitories.organization_id` (ревизия `0043_dormitories_organization`).
Все операционные таблицы висят на `dormitory_id`, поэтому дочерние строки наследуют
принадлежность от корня: никакой своей колонки организации у них нет, и
денормализации в этом варианте нет.

- Организация берётся **только из сессии** (`users.active_organization_id` +
  строка членства), никогда из тела запроса: `organization_id` нет ни в одном
  запросе или ответе API.
- Чужой объект отвечает тем же `404` «Общежитие не найдено», что и несуществующий.
  `403` за изоляцию не используется намеренно — иначе по коду ответа видно, что
  объект с таким номером существует.
- Гейт один и живёт в `app/access.py`: `own_dormitory(db, dormitory_id, membership)`
  для проверки внутри обработчика и зависимость `OwnDormitory` для путей с
  `{dormitory_id}`. Проверка стоит **раньше** блокировки общежития и любых
  изменений, поэтому чужая строка не успевает ни заблокироваться, ни измениться.
- Если `dormitory_id` приходит телом запроса, зависимость на путь его не
  закрывает: обработчик вызывает `own_dormitory` сам. Такие ручки перечислены в
  белом списке `BODY_GUARDED` инвентарного теста.
- Выборки «по всем общежитиям» (`/api/dormitories`, `/api/dashboard`,
  `/api/statistics/sources`, `/api/personnel`, каталоги вкладок) ограничены
  общежитиями своей организации.

**Новый маршрут обязан объявлять гейт.** Это проверяет инвентарный тест
`tests/test_route_guard_inventory.py`: он идёт по маршрутам приложения, и маршрут с
`{dormitory_id}` без `OwnDormitory` (или ручка с `dormitory_id` в теле, которой нет в
`BODY_GUARDED`) валит прогон. Мёртвые записи белого списка тоже валят его. Ослаблять
тест нельзя: он и есть механизм, которым изоляция держится без памяти разработчика.

Миграция заполняет принадлежность существующих общежитий по автору
(`dormitories.created_by_id` → `users.active_organization_id`). Общежитие, которое
привязать нечем, **останавливает миграцию** с перечнем `id`: судьбу остатка решает
владелец данных, а не миграция. `downgrade` снимает `NOT NULL`, индекс и колонку —
вместе с привязкой.

## Журнал действий

Каждый write-запрос к `/api` (`POST`, `PUT`, `PATCH`, `DELETE`) оставляет строку в
таблице `audit_events`: кто, когда, что за действие, над каким маршрутом, с каким
статусом и телом. Журнал собирает middleware в `app/main.py`, правила и запись
живут в `app/audit.py` — ни одна из существующих ручек о нём не знает и не
меняется.

Запись — **fail-closed**: строка уходит в тот же коммит, что и само действие
(слушатель `before_commit`), поэтому в базе либо есть и действие, и его строка,
либо нет ни того ни другого. Если строку записать не удалось, коммит отменяется, а
клиент получает `503` с текстом в `detail` — действие не выполнено. Одна строка
на один коммит: у ручек с несколькими коммитами строк будет несколько. Вход, выход
и отказы (4xx/422) не коммитят вовсе — их строку middleware пишет после ответа,
уже best-effort, зато с настоящими `status` и `duration_ms`; у таких строк `status`
и `duration_ms` заполнены, а у атомарных пусты (на момент коммита код ответа ещё
неизвестен).

Что попадает в строку:

- `actor_id` и `organization_id` — из сессии (`get_current_user`); у входа,
  регистрации и восстановления пароля актора нет;
- `actor_name` — ФИО автора **снимком на момент записи**: копия `users.full_name`
  (ревизия `0044_audit_actor_name`), а не join на `users` при чтении, поэтому
  смена фамилии не переписывает уже собранный журнал. Здесь ФИО лежит **без
  маскирования** — маска относится к телам запросов и снимкам `changes`; это
  осознанно: журнал читает только владелец, а ФИО сотрудников ему и так доступны
  в разделе «Организация». Следствия: уволенный сотрудник остаётся в журнале по
  имени, а строки вида `security` живут 730 дней. У записей без сессии (вход,
  регистрация, восстановление пароля) и у строк старше ревизии `0044` значение
  `NULL`: backfill не делается, экран показывает такие строки как
  «Сотрудник №<actor_id>»;
- `path` — шаблон маршрута (`/api/dormitories/{dormitory_id}`), а не адрес с
  подставленным идентификатором; `path_params` — сами значения;
- `kind` — `security` (вход, организация, биллинг, тарифы, настройки общежития),
  `data` (остальная работа с данными) или `noise` (автоподстановка ячеек);
- `request_body` — только JSON, не длиннее `AUDIT_BODY_LIMIT_BYTES` (2 КБ), и
  только после очистки: значения `password`, `new_password`, `password_hash`,
  `token`, `authorization` и `cookie` заменяются на `***` без отпечатка, а
  персональные данные — на маску с отпечатком: `full_name` → `И*** И*** И***`,
  `phone` → `+7***22`, `email` → `i***@example.com`, свободный текст (`notes`,
  `reason`, `additional_info`, `text`, `comment`, `description`) — только длина и
  отпечаток `{"_masked": "free_text", "length": …, "fp": …}`. Отпечаток —
  `HMAC-SHA256` с секретом `JWT_SECRET` и своим доменом: одинаковые значения дают
  одинаковый отпечаток, разные — разный, а само значение не восстанавливается.
  Реквизиты (`inn`, `kpp`, `ogrn`, `address`, `buyer_*`), названия объектов
  (`name`), `personnel_number`, `medical_book` и `citizenship` не маскируются:
  по ним и ищут в журнале. Тело длиннее `AUDIT_BODY_READ_LIMIT_BYTES` (64 КБ) и
  тело `multipart/form-data` (импорт «Мест») не читается вовсе.

Снимок изменений лежит в `changes` той же строки: список записей вида
`{"entity", "id", "op", "field", "old", "new"}` — по одной записи на колонку,
которую затронул коммит. `op` — `insert` (значения в `new`), `update` (обе
стороны) или `delete` (значения в `old`), `entity` — имя таблицы, `id` —
идентификатор строки. Пустая колонка в снимок не попадает. Собирается он по
состоянию сессии, а не по телу запроса, и копится за транзакцию: ручки пишут и
промежуточными `flush`, после которых история изменений атрибутов уже пуста.
Поэтому строка журнала пишется не только на write-методах: правило — «в сессии
есть реальные изменения **или** метод запроса write». Так в журнал попадает
`GET` вкладки таблицы, который создаёт недостающие столбцы и коммитит, а коммит
без изменений оставляет `changes = NULL`.

Значения снимка проходят ту же очистку, что и тело запроса (`redact` → `mask` →
`truncate`), иначе маскирование ПДн обессмысливалось бы: у `full_name`, `phone` и
`email` в `changes` лежит маска с отпечатком, у `password_hash` — только `***`
без отпечатка, а реквизиты организации видны целиком. Из снимка исключены таблицы
`activation_tokens`, `recovery_requests` (там отпечатки секретов, а ключи
`token_hash` и `identifier_hash` список маскирования не знает), а также
производные `employee_aliases` и `employee_events`: они повторяют строку
проживающего под ключами `value`, `raw_value` и `snapshot`, по которым
маскирование не срабатывает.

Объём строки от снимка растёт: замер — с ~194 байт до ~871-1223 байт. Чтобы рост
был ограничен, снимок ужимается: не больше `DIFF_LIMIT` (10) записей на строку,
значение не длиннее `CHANGE_VALUE_LIMIT` (300) символов, а остаток сворачивается в
`{"_omitted": N}`. Полного снимка широкой строки при этом не будет — это
осознанный компромисс в пользу объёма журнала. Отсюда же следствие срока хранения:
при 300 действиях на человека журнал растёт с ~38 до ~100 ГБ в год, и выбор
между сокращением срока для вида `data` и планированием диска под 730 дней
остаётся за владельцем.

Хранение — месячными партициями (`audit_events_2026_10`): ревизия
`0036_audit_events` заводит таблицу, партиции на текущий и следующие 12 месяцев и
`DEFAULT`-партицию как страховку от пропущенного месяца, а `0038_audit_changes_column`
добавляет колонку `changes`, `0044_audit_actor_name` — колонку `actor_name` (на
партиционированной таблице это метаданные: колонка наследуется всеми партициями,
данные не переписываются);
`app.audit.ensure_partitions`
досоздаёт их при старте и на смене месяца, а строка, попавшая в `DEFAULT`,
сопровождается WARNING в логе. Сроки хранения: 730 дней для `security` и 90 дней
для `data` и `noise` (`AUDIT_RETENTION_DAYS_SECURITY`, `AUDIT_RETENTION_DAYS_NOISE`);
устаревшее убирает `app.audit.prune_audit` — тоже при старте и на смене месяца.
Настройки журнала целиком лежат в `app/config.py` и начинаются с `audit_`/`AUDIT_`;
выключение — `AUDIT_ENABLED=false`.

Журнал — не бизнес-данные: в дамп кабинета он не входит.

```bash
pg_dump -T 'audit_events*' ...
```

## Стек

- **Backend** — FastAPI (Python).
- **Frontend** — React + TypeScript.
- **База данных** — PostgreSQL, запуск через Docker Compose.

## Структура

```
.
├── app/
│   ├── backend/          — FastAPI: app/, alembic/, tests/, Dockerfile
│   └── frontend/         — React + TypeScript: src/, Dockerfile, nginx.conf
├── docker-compose.yml    — стенд: db + api + web + bot
├── .env.example          — значения стенда по умолчанию (.env переопределяет)
└── README.md
```

## Запуск стенда

```bash
docker compose up -d --build
```

Адреса по умолчанию:

- Frontend — http://localhost:8080
- API — http://localhost:8001

Если на машине несколько стендов проекта, запускайте свой под отдельным именем,
чтобы не задеть контейнеры и том базы соседнего стенда:

```bash
docker compose -p <имя-стенда> up -d --build
```

## Процесс работы

- Базовая ветка — `main`, напрямую в неё не коммитят.
- Задача берётся из issue с меткой `ready-for-dev`; ветка задачи —
  `feature/<номер>-<краткий-слаг>`, например `feature/1-readme`.
- Итог оформляется pull request в `main`; мерж делает человек.
- После открытия pull request issue получает метку `ready-for-test`.
- Разработчик отвечает за статический анализ и юнит-тесты; E2E-проверки
  (Playwright), визуальные эталоны и отчёты о доступности — за тестировщиком.
